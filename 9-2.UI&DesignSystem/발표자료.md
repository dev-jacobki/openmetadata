## 1. Frontend 빌드 체계

OpenMetadata UI는 브라우저에서 실행되는 React 애플리케이션, 이를 보조하는 공유 UI 패키지, 개발 환경을 준비하는 Node·Yarn, 그리고 화면과 타입의 기준이 되는 JSON Schema가 함께 구성한다. 먼저 각 요소가 어디에 있고 어떤 결과를 만드는지 정리한 뒤, 다음 절에서 Service 연결 화면이 이 구조를 어떻게 사용하는지 본다.

### 1.1 Frontend 소스 구조

`openmetadata-ui/src/main/resources/ui/src`는 실제 화면을 실행하는 애플리케이션의 소스 루트다. 폴더는 화면, 재사용 UI, 상태·컨텍스트, API 호출, Schema 산출물처럼 역할에 따라 나뉜다.

```text
src/
├── pages/                  URL에 대응하는 업무 화면
├── components/             화면 안에서 조합하는 도메인·공통 UI
├── context/ · hooks/       인증·Theme·사용자 선택값 같은 공유 상태와 동작
├── rest/                   OpenMetadata Server REST API 호출
└── generated/ · jsons/     Schema에서 준비한 TypeScript 타입과 Form용 JSON
```

- `pages`는 URL에 대응하는 화면 단위다. Service 추가, Theme, Persona, My Data 같은 업무 화면이 이 계층에서 시작한다.
- `components`는 여러 화면에서 조합하는 도메인·공통 UI다. `pages`가 화면의 진입점이라면 `components`는 화면 안의 기능 단위다.
- `context`, `hooks`는 인증, Theme, 사용자 선택값처럼 여러 화면이 공유하는 상태와 동작을 연결한다.
- `rest`는 OpenMetadata Server API 호출을, `generated`와 `jsons`는 JSON Schema에서 준비한 타입·Form용 JSON을 담당한다.

위 트리는 정적인 책임 구분이다. 실제 시작 순서는 `index.tsx → AppRoot → App / AuthProvider / AppRouter → AuthenticatedApp → AuthenticatedRoutes → AppContainer → pages`다. 즉, 공통 설정과 인증을 먼저 준비한 뒤 실제 업무 화면을 표시한다.

![Frontend 실행 흐름](발표자료-assets/frontend-build-flow.svg)

### 1.2 `openmetadata-ui-core-components` 구조

`openmetadata-ui-core-components`는 앱과 별도로 빌드되는 공유 UI 패키지다. 반복 사용되는 Button·Input·Table 같은 컴포넌트와 색상·Theme·스타일 규칙을 한 곳에서 제공한다. 앱 전체를 대체하는 프레임워크가 아니라, 여러 화면이 같은 UI 기반을 쓰도록 만드는 공통 계층이다.

```text
src/
├── components/
│   ├── base/               Button, Input, Select 같은 기본 구성요소
│   ├── application/        Table, Modal, DatePicker 같은 조합 구성요소
│   └── foundations/        디자인 토큰을 반영한 기반 구성요소
├── theme/ · colors/        createMuiTheme, palette·색상 유틸리티
├── styles/                 Tailwind tw: 접두사와 공통 스타일
├── utils/ · types/ · hooks/ 공유 유틸리티, 타입, Hook
└── index.ts                앱이 import하는 공개 API
```

`src/index.ts`가 `components`, `theme`, `colors`, `utils`, `types`를 공개 API로 다시 export한다. 앱은 내부 파일 경로가 아니라 패키지 import를 통해 이 API를 사용한다.

```typescript
import { Button, createMuiTheme } from '@openmetadata/ui-core-components';
```

저장소 폴더명은 `openmetadata-ui-core-components`, 앱에서 사용하는 패키지명은 `@openmetadata/ui-core-components`다. 현재 저장소에 `openmetadata-ui-components`라는 별도 패키지는 없다.

### 1.3 UI 라이브러리가 공존하는 이유

현재 UI는 하나의 라이브러리로 만들어지지 않았다. 기존 화면을 구성하는 Ant Design, MUI Theme가 필요한 컴포넌트, 새 공유 UI 패키지가 공존한다. 같은 Theme 설정을 각 계층에 전달해 화면의 색상과 상태 표현을 맞추는 구조다.

| 계층 | 현재 쓰임 | Theme 적용 | 새 코드에서의 기준 |
|---|---|---|---|
| Ant Design | 기존 앱 화면의 Form·Table·기본 UI | `AntDConfigProvider`가 palette와 `--ant-*` CSS 변수를 적용 | 기존 Ant Design 화면을 수정할 때는 해당 화면의 패턴을 따른다. 임의로 다른 라이브러리로 교체하지 않는다. |
| MUI | MUI Theme가 필요한 컴포넌트 | `createMuiTheme()`의 결과를 `ThemeProvider`가 전달 | MUI 컴포넌트가 필요하면 공유 패키지의 `createMuiTheme()`로 만든 Theme를 사용한다. |
| `@openmetadata/ui-core-components` | 재사용 UI, 디자인 토큰, Theme·색상 유틸리티 | `UntitledUIThemeProvider`가 brand color를 `--tw-*` CSS 변수로 제공 | 새로 만드는 범용 공유 컴포넌트는 이 패키지를 우선한다. |

`AppRoot`는 하나의 `customTheme`을 `applicationConfig`에 보관하지만, 각 라이브러리는 위와 같이 다른 Provider와 token으로 이를 소비한다. 이 때문에 기존 화면과 새 공유 UI가 공존해도 같은 강조색·상태색 기준을 유지한다.

공유 패키지의 컴포넌트 기반은 MUI나 Ant Design 자체가 아니라 `react-aria-components`와 Untitled UI 패턴이다. 스타일은 Tailwind의 `tw:` 접두사와 디자인 토큰을 사용해 기존 Ant Design·Less 스타일과 충돌하지 않게 한다. 따라서 새 공유 컴포넌트를 만들 때는 Ant Design이나 MUI 스타일을 직접 섞기보다, 패키지의 컴포넌트·토큰·접근성 기반을 따르는 것이 저장소의 개발 기준이다.

### 1.4 Node·Yarn과 개발 서버

Node.js는 브라우저 화면을 대신 실행하는 환경이 아니다. 개발자가 Vite 같은 JavaScript 기반 도구를 실행하는 런타임이다. React 화면 자체는 Vite가 제공한 파일을 브라우저가 실행한다.

| 도구 | 이 자료에서의 역할 |
|---|---|
| Node.js | Vite를 포함한 Frontend 개발 도구가 실행되는 런타임이다. |
| Yarn | 필요한 패키지를 설치하고, 프로젝트가 정의한 개발 명령을 실행한다. |
| Vite | `yarn start`로 개발 서버를 열고, 변경한 Frontend 코드를 브라우저에 제공한다. |

개발 시작은 다음 흐름으로 이해하면 충분하다.

1. `make yarn_install_cache`가 앱 UI와 공유 UI 패키지에 필요한 의존성을 준비한다.
2. `make yarn_start_dev_ui`가 앱의 `yarn start`, 즉 Vite 개발 서버를 실행한다.
3. 브라우저가 개발 서버에서 받은 React 코드를 실행하고, 파일 변경을 화면에 반영한다.

```bash
make yarn_install_cache
make yarn_start_dev_ui
```

### 1.5 JSON Schema: JSON 데이터의 계약

JSON Schema는 “어떤 JSON을 유효한 데이터로 볼 것인가”를 선언하는 형식이다. 특정 화면이나 프로그래밍 언어에 묶이지 않으며, 데이터의 형태와 검증 규칙을 함께 적는 계약이다. OpenMetadata에서는 이 계약을 기준으로 타입을 만들고, Service 연결 화면은 필요한 입력 구조를 읽는다.

JSON 값과 JSON Schema는 구분해야 한다. 연결 설정 값은 `{"hostPort":"db:3306"}`처럼 실제 입력 데이터이고, Schema는 `hostPort`가 string이어야 한다는 규칙이다. Schema는 세 가지 역할을 함께 한다.

- **구조 정의:** 필드 이름, 자료형, 중첩 object·array 구조를 정한다.
- **검증 기준:** 필수 값, 허용 선택지, 인증 방식처럼 유효한 입력 범위를 정한다.
- **공유 기준:** 공통 인증·SSL 규칙을 `$ref`로 재사용하고, 생성된 타입과 Form이 같은 필드 구조를 보게 한다.

| Schema 키워드 | 의미 | Connection 설정에서의 예 |
|---|---|---|
| `type` | 값의 기본 형태 | `string`, `boolean`, `object` |
| `properties` | object 안에 둘 필드 | `hostPort`, `username`, `authType` |
| `required` | 반드시 받아야 할 필드 | `hostPort`, `username` |
| `enum`, `default` | 제한된 선택지와 기본값 | Service Type, Connection Scheme |
| `oneOf` | 여러 구조 중 하나를 선택 | Basic·IAM 등 인증 방식 |
| `$ref` | 다른 Schema의 공통 정의를 참조 | SSL, 인증, Filter Pattern |

MySQL Connection Schema는 이 규칙을 실제로 사용한다. `authType`의 각 선택지는 별도 인증 Schema를 참조하고, 필수 항목은 `required`에서 한 번에 선언한다.

```json
"authType": {
  "oneOf": [
    { "$ref": "./common/basicAuth.json" },
    { "$ref": "./common/iamAuthConfig.json" }
  ]
},
"required": ["hostPort", "username"]
```

OpenMetadata에서 원본 Schema는 `openmetadata-spec`에 있고, 한 정의가 두 방향으로 사용된다.

| 결과 | 목적 | Frontend에서의 위치 |
|---|---|---|
| TypeScript 타입 | API 요청·응답과 props가 같은 필드 구조를 사용하게 하는 정적 타입 | `src/generated` |
| Form용 JSON asset | 브라우저가 Service별 입력 필드와 기본 검증 규칙을 읽게 하는 runtime 데이터 | `src/jsons/connectionSchemas` |

`quicktype`은 첫 번째 TypeScript 타입만 만든다. Form용 JSON은 브라우저가 읽는 별도 asset이며, 공통 Schema 참조를 Form에서 사용할 수 있는 형태로 준비한다. 따라서 Schema가 필드의 구조·검증을 정의해도 화면 전체가 자동으로 결정되지는 않는다. 다음 절의 UI는 `uiSchema`, custom field, 별도 필터 단계로 표시 순서와 추가 동작을 보완한다.

## 2. 커넥터 UI 통합 패턴

1절의 JSON Schema가 실제 화면에서 쓰이는 대표 사례가 Service 추가 화면이다. 여기서 먼저 Service가 무엇을 뜻하는지 정리하고, 선택한 Service가 어떻게 연결 설정 Form이 되는지 본다.

### 2.1 Service는 외부 시스템의 연결 등록 단위

이 문맥의 Service는 일반적인 백엔드 마이크로서비스를 뜻하지 않는다. OpenMetadata가 메타데이터를 수집하거나 연결 설정을 보관할 외부 플랫폼의 등록 단위다. 하나의 Service에는 연결 방식과 그 아래에서 관리할 메타데이터 유형이 함께 정해진다.

| Service Category | Service Type 예시 | OpenMetadata가 연결하는 대상 |
|---|---|---|
| Database | MySQL, PostgreSQL | Database·Schema·Table 같은 데이터 자산 |
| Messaging | Kafka | Topic 같은 메시지 자산 |
| Dashboard | Superset | Dashboard·Chart 같은 BI 자산 |

`serviceCategory`는 Database·Messaging처럼 큰 계열을 고르고, `serviceType`은 MySQL·Kafka·Superset처럼 구체적인 제품을 고른다. 이 두 값이 어떤 Connection Schema와 Form을 읽을지 결정한다.

### 2.2 Service 선택이 연결 설정 Form이 되는 과정

**UI 페이지:** `Settings > Services > Add New Service`

Service 추가 화면은 Service 종류를 먼저 정한 뒤 기본 정보, 연결 설정, 필터 설정을 차례로 입력한다. 연결 설정 단계가 선택한 Service의 Connection Schema를 사용하는 부분이다.

| 단계 | 화면에서 정하는 값 | 다음 단계에 주는 정보 |
|---|---|---|
| Service 선택 | `serviceCategory`, `serviceType` | 선택할 Connection Schema의 기준 |
| 기본 정보 | Service 이름·설명 | OpenMetadata에 등록할 Service 정보 |
| 연결 설정 | host, 인증 방식, 옵션 등 | 선택 Schema에 맞는 연결 값 |
| 필터 설정 | 포함·제외 패턴 | 수집 대상을 제한하는 규칙 |

브라우저에서는 `getConnectionSchemas()`가 Category로 Service 유틸리티를 고르고, Type으로 해당 Form Schema를 찾는다. `ConnectionConfigForm`은 기본 필터 필드를 분리한 뒤 `FormBuilder`에 Schema와 `uiSchema`를 전달한다. `FormBuilder`는 RJSF와 AJV validator를 이용해 입력 UI와 검증을 구성한다.

![서비스 설정 UI 전체 흐름](발표자료-assets/schema-type-flow.svg)

### 2.3 새 커넥터가 화면에 나타나기 위한 연결점

새 Connection Schema 파일만 추가해도 Service 선택 목록과 연결 Form이 자동으로 완성되지는 않는다. 화면에 연결하려면 다음 세 위치가 같은 Service Type을 알아야 한다.

1. 원본 Connection JSON Schema가 연결 필드와 검증 규칙을 정의한다.
2. Service 엔티티의 Type enum이 선택 화면에 표시할 유형을 제공한다.
3. `ServiceConnectionUtils`의 Category별 분기가 Type에 맞는 Form Schema를 반환한다.

```typescript
const { connSch } = getConnectionSchemas({
  serviceCategory,
  serviceType,
});
```

이 세 연결점이 맞아야 선택 화면의 제품명, runtime Form Schema, 저장할 연결 값이 같은 Service를 가리킨다.

## 3. Theme & 브랜딩 커스터마이징

Theme는 색상만 바꾸는 기능이 아니다. 기존 Ant Design 화면, MUI Theme가 필요한 컴포넌트, 새 UI 패키지의 토큰에 같은 설정을 전달하고, 브랜드 이미지는 별도 경로로 적용한다.

### 3.1 Theme에서 조정하는 값

**UI 페이지:** `Settings > Preferences > Theme`

| 설정 그룹 | 대표 필드 | 적용 대상 |
|---|---|---|
| 기본 강조색 | `primaryColor` | 버튼, 링크, Navigation의 강조·선택 상태 |
| 상호작용 상태 | `hoverColor`, `selectedColor` | hover·선택 상태 |
| 의미 색상 | `errorColor`, `successColor`, `warningColor`, `infoColor` | 오류·성공·경고·정보 상태 |
| 패널 배경 | `panelBackgroundColor` | Landing Page welcome panel의 기본 배경색 |
| 브랜드 자산 | logo, monogram, favicon 경로 | 헤더·로그인·브라우저 아이콘 |

### 3.2 하나의 Preference를 여러 UI 계층에 적용한다

`uiThemePreference.json`은 색상 설정 `customTheme`과 이미지 경로 설정 `customLogoConfig`를 함께 저장한다. 앱 시작 시 `AppRoot`가 이 Preference를 읽어 `applicationConfig`에 둔다.

```typescript
setApplicationConfig({
  ...themeData,
  customTheme: getThemeConfig(themeData.customTheme),
});
```

`getThemeConfig()`은 빠진 기본·상태·의미 색상을 보완한다. palette나 CSS 변수는 이 함수가 아니라 각 UI Provider가 만든다. `customTheme`은 Ant Design, MUI, Untitled UI Provider로 전달되고, `customLogoConfig`는 `BrandImage`의 logo·monogram과 `AppRoot`의 favicon에 따로 적용된다.

여기서 Untitled UI는 새 공유 UI가 따르는 디자인 시스템 패턴·토큰 계층이다. 별도의 관리자 화면이나 독립 제품이 아니라, 이 앱 안에서 공유 컴포넌트의 색상·상태·spacing 기준을 제공한다. `UntitledUIThemeProvider`가 brand color를 CSS 변수 `--tw-*`로 만들고, 공유 UI 컴포넌트가 React Aria와 Tailwind `tw:` 클래스로 이를 소비한다.

![설정값이 화면에 도달하는 경로](발표자료-assets/theme-flow.svg)

이 구조 때문에 Theme 설정은 라이브러리마다 다른 구현을 유지하면서도 사용자가 보는 강조색·상태색·브랜드 이미지를 같은 Preference에서 관리할 수 있다.

## 4. Persona 기반 개인화

Persona는 사용자의 직무나 업무 유형에 맞춰 Navigation과 Page 구성을 선택하는 엔티티다. 예를 들어 Data Engineer·Data Consumer처럼 업무에서 보는 자산과 시작 화면이 다른 사용자를 구분할 수 있다. 권한을 판단하는 Role과 다르다. Role이 “무엇을 할 수 있는가”를 정한다면 Persona는 “어떤 화면 구성을 우선 보여주는가”를 정한다.

### 4.1 Persona가 UI 구성을 선택하는 방식

**UI 페이지:** `Settings > Personas`

로그인 시 서버가 사용자 기본 Persona를 결정해 `User.defaultPersona`에 담는다. Frontend Store는 이 값을 현재 선택 상태인 `selectedPersona`로 초기화한다. 화면은 선택된 Persona의 FQN으로 문서를 조회해 Navigation과 Page 구성을 읽는다.

![Persona 개인화 흐름](발표자료-assets/persona-flow.svg)

`Persona.default`는 사용자의 지정 Persona가 없을 때 서버가 적용하는 기본값이다. Frontend가 `Persona.default`를 직접 선택하는 것이 아니라, 서버가 정한 `User.defaultPersona`를 받아 사용한다.

### 4.2 현재 Persona가 바뀌면 문서를 다시 읽는다

Frontend Store에는 현재 로그인 사용자와 현재 선택 Persona가 함께 저장된다.

```typescript
const { defaultPersona } = user;
set({ currentUser: user, selectedPersona: defaultPersona });
```

사용자가 Persona를 변경하면 `selectedPersona`가 바뀌고, 이를 구독하는 화면은 새 Persona 문서를 다시 조회한다. 역할 권한을 바꾸지 않고도 사용자별 Navigation과 시작 화면 구성을 전환할 수 있는 이유다.

### 4.3 Persona 문서는 Page와 Navigation을 함께 제공한다

`useCustomPages(pageType)`는 선택 Persona의 `fullyQualifiedName`으로 `persona.<FQN>` 문서를 찾는다. 문서의 `pages`에서는 요청한 `pageType` 하나를 고르고, `navigation`은 별도 상태로 적용한다.

```typescript
const doc = await getDocumentByFQN(pageFQN);
setCustomizedPage(doc.data?.pages?.find((p) => p?.pageType === pageType));
setNavigation(doc.data?.navigation);
```

따라서 화면 코드가 Persona 이름을 조건문으로 비교하지 않는다. 같은 렌더러가 선택 Persona에 연결된 문서 데이터를 읽어 Page와 Navigation을 구성한다.

## 5. 커스터마이즈 가능한 Landing Page

Landing Page는 Persona 문서의 `pages` 중 `pageType=LandingPage`인 Page에 저장된다. 편집 화면의 배치를 캡처해 보관하는 방식이 아니라, 위젯 ID와 grid 좌표가 담긴 `layout`을 저장하고 실제 Home 화면이 다시 해석한다.

### 5.1 Landing Page가 저장하는 Layout

**설정 UI 페이지:** `Settings > Personas > <Persona> > Customize UI > Landing Page`

**렌더링 UI 페이지:** `Home / My Data`

Landing 구현은 `Page.layout`을 `WidgetConfig[]`로 사용한다. 각 항목은 어떤 위젯인지와 grid에서 어느 위치·크기로 표시할지를 함께 기록한다.

| 필드 | 의미 |
|---|---|
| `i` | grid의 고유 ID이자 위젯 종류를 찾는 키 |
| `x`, `y` | grid 안의 시작 좌표 |
| `w`, `h` | 위젯의 너비와 높이 |
| `static`, `isDraggable` | 이동 가능 여부 |
| `config`, `children` | 위젯별 추가 설정과 하위 구성 |

`i`에는 `KnowledgePanel.ActivityFeed`, `KnowledgePanel.KPI`, `KnowledgePanel.MyTask` 같은 값이 들어간다. Landing Page 위젯 키에는 Announcements와 Recently Viewed도 정의되어 있으며, Activity Feed·KPI·Tasks·Recently Viewed처럼 업무 맥락에 맞는 panel을 선택해 구성하는 구조다. 같은 위젯을 Persona마다 다른 위치·크기로 보이게 할 수 있다.

### 5.2 편집한 Layout을 저장하고 다시 렌더링한다

편집 화면은 `react-grid-layout`의 `data-grid`에 각 `WidgetConfig`를 전달한다. 현재 grid는 resize를 비활성화하고, 드래그 이동·위젯 추가·제거로 바뀐 배열을 Persona의 Landing Page 데이터에 저장한다. 위젯 너비는 추가 시 선택한 `widgetSize`로 정한다.

`Home / My Data`는 선택 Persona 문서를 다시 조회하고 같은 `layout`을 순회한다. 즉, 편집 화면의 모양을 저장하는 것이 아니라 저장된 좌표와 위젯 ID를 실제 화면에서 다시 해석한다.

![하나의 Layout을 편집하고 다시 렌더링한다](발표자료-assets/landing-layout-flow.svg)

선택 Persona가 없거나 문서 조회에 실패하거나 저장된 `layout`이 비어 있으면 `CustomizeMyDataPageClassBase`의 `defaultLayout`을 사용한다. 기본 layout에는 Activity Feed, Data Assets, My Data, KPI, Total Assets, Following이 들어 있다.

### 5.3 위젯 ID가 React 컴포넌트를 고른다

`WidgetConfig.i`는 React Grid Layout의 key이면서 실제 위젯 컴포넌트를 찾는 키다.

```tsx
layout.map((widget) => (
  <div data-grid={widget} key={widget.i}>
    {getWidgetFromKey({ widgetConfig: widget, currentLayout: layout })}
  </div>
));
```

`getWidgetFromKey()`는 `widgetConfig.i`를 `getWidgetsFromKey()`에 전달해 Activity Feed, KPI, My Task 같은 React 컴포넌트를 선택한다. 따라서 위젯 구현과 Persona별 배치 데이터는 분리되며, 같은 위젯을 사용하면서도 Persona마다 포함 여부와 위치를 다르게 설정할 수 있다.
