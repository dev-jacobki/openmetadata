## 1. Frontend 구조와 공유 컴포넌트

OpenMetadata Frontend는 실행 가능한 애플리케이션 UI와 재사용 가능한 공유 UI 패키지로 나뉜다. 화면 전환과 도메인 로직은 애플리케이션 UI가 담당하고, 반복되는 컴포넌트와 Theme 기반은 공유 UI 패키지가 제공한다.

### 1.1 Frontend 전체 구조

애플리케이션 내부 코드는 역할별로 분리되어 있다.

| 영역 | 역할 |
|---|---|
| `pages` | URL에 대응하는 화면 단위 |
| `components` | 화면을 구성하는 도메인·공통 컴포넌트 |
| `hooks`, Store | 사용자·Persona·설정 등 UI 상태 관리 |
| `rest` | OpenMetadata REST API 호출 |
| `generated`, `jsons` | Schema에서 만든 타입과 런타임 Form Schema |

브라우저에서 앱이 시작되면 `index.tsx`가 `AppRoot`를 렌더링한다. `AppRoot`가 전역 설정과 초기 인증 상태를 준비하고, `App`은 `AuthProvider`로 `AppRouter`를 감싼다. 인증 분기 뒤에는 `AuthenticatedApp`, `AuthenticatedRoutes`, `AppContainer`를 거쳐 실제 Page가 렌더링된다.

![Frontend 전체 구조](발표자료-assets/frontend-build-flow.svg)

### 1.2 `openmetadata-ui-core-components`

`openmetadata-ui`가 전체 화면을 실행하는 앱이라면, `openmetadata-ui-core-components`는 여러 화면에서 재사용할 UI 기반을 묶은 패키지다. 앱 내부의 기존 컴포넌트와 Ant Design 사용을 모두 대체하는 구조가 아니라, 공통으로 사용할 새 컴포넌트와 Theme API를 제공하는 계층이다.

| 공개 영역 | 제공 내용 |
|---|---|
| `components` | Button, Input, Card, Table, 내비게이션 구성요소 등 |
| `theme` | `createMuiTheme`과 Theme 타입 |
| `colors` | 공통 색상과 palette 도구 |
| `utils` | 공유 컴포넌트에서 사용하는 유틸리티 |

저장소의 모듈명은 `openmetadata-ui-core-components`, 앱에서 사용하는 패키지명은 `@openmetadata/ui-core-components`다. 현재 저장소에 `openmetadata-ui-components`라는 별도 패키지는 없다.

앱의 `package.json`은 공유 패키지를 로컬 경로로 연결한다.

```json
"@openmetadata/ui-core-components":
  "link:../../../../../openmetadata-ui-core-components/src/main/resources/ui"
```

공유 패키지의 `src/index.ts`는 `theme`, `colors`, `components`, `utils`, `types`를 하나의 공개 API로 다시 export한다. 앱에서는 내부 파일 경로가 아니라 이 공개 API를 import한다.

```typescript
import { Button, createMuiTheme } from '@openmetadata/ui-core-components';
```

### 1.3 개발 빌드 순서

`make yarn_install_cache`는 앱 UI 디렉터리에서 `yarn install`을 실행한다. 이때 앱의 `preinstall`이 먼저 실행되어 저장소 의존성을 설치하고, `openmetadata-ui-core-components`를 설치·빌드한다. 공유 패키지의 `dist`가 준비된 뒤 앱 의존성의 로컬 링크가 이를 사용한다.

```bash
cd ../../../../..
yarn install --frozen-lockfile
cd openmetadata-ui-core-components/src/main/resources/ui
yarn install && yarn build
```

설치가 끝난 뒤 `make yarn_start_dev_ui`는 앱의 `yarn start`, 즉 Vite 개발 서버를 실행한다.

```bash
make yarn_install_cache
make yarn_start_dev_ui
```

공유 컴포넌트의 공개 API나 Theme 구현을 변경하면 core components 빌드 결과가 먼저 갱신되어야 앱에서 같은 변경을 확인할 수 있다.

## 2. JSON Schema와 커넥터 UI

서비스 연결 Schema는 두 산출 경로에서 사용된다. 하나는 별도 코드 생성 작업으로 만드는 TypeScript 타입이고, 다른 하나는 UI 설치 과정에서 만드는 Form용 JSON asset이다. 후자는 브라우저 실행 중 선택한 연결 유형의 Form을 구성할 때 읽힌다.

### 2.1 서비스 설정 UI 전체 흐름

**UI 페이지:** `Settings > Services > Add New Service`

서비스 추가 화면은 다음 순서로 진행된다.

| 단계 | 화면에서 결정하는 값 |
|---|---|
| 서비스 선택 | `serviceCategory`, `serviceType` |
| 기본 정보 | 서비스 이름과 설명 |
| 연결 설정 | 선택한 서비스의 Connection Schema 기반 입력값 |
| 필터 설정 | 포함·제외 패턴 등 별도 필터 입력값 |

연결 설정 단계에서 `serviceCategory`는 Database·Messaging·Dashboard 같은 서비스 계열을 선택하고, `serviceType`은 MySQL·Kafka·Superset 같은 구체적인 연결 유형을 선택한다. 선택 결과가 런타임 Connection Schema를 찾는 기준이 된다.

![서비스 설정 UI 전체 흐름](발표자료-assets/schema-type-flow.svg)

### 2.2 JSON Schema를 사용하는 두 경로

#### TypeScript 타입 생성

`json2ts.sh`는 `openmetadata-spec`의 JSON Schema를 `quicktype`에 전달하고, 같은 상대 경로를 유지한 TypeScript 타입을 `src/generated`에 만든다. 생성 타입은 API 응답, 요청 데이터, 컴포넌트 props가 같은 필드 구조를 사용하도록 한다.

```bash
quicktype -s schema "$tmp_schema_file" \
  -o "$output_file" --just-types
```

#### Form용 JSON asset 생성

`parseSchemas.js`는 `connections` 아래의 Schema를 읽고 `$ref`를 dereference·bundle한 JSON을 `src/jsons/connectionSchemas/connections`에 만든다. 이 결과는 TypeScript 타입이 아니라 브라우저에서 Form을 구성할 때 읽는 런타임 Schema다.

```javascript
await main(
  'connTemp',
  'schema/entity/services/connections',
  'src/jsons/connectionSchemas/connections',
  true
);
```

따라서 `json2ts.sh`가 Form을 만드는 것은 아니다. 타입 생성은 정적 타입 검사에 사용되고, 설치 과정에서 실행되는 `parseSchemas.js`의 결과는 브라우저 Form의 입력 필드와 검증 규칙에 사용된다.

런타임 Schema의 `type`, `enum`, `oneOf`, `required`, `default`가 기본 입력 구조와 검증 조건을 정한다. UI 코드는 `uiSchema`, custom field·template, 별도 필터 단계, 제출 처리를 추가한다.

### 2.3 선택한 서비스가 Form이 되는 과정

`ConnectionConfigForm`은 선택된 `serviceCategory`와 `serviceType`을 `getConnectionSchemas()`에 전달한다. 처리 순서는 다음과 같다.

1. `serviceCategory`로 Database·Messaging 등 서비스 유틸리티를 선택한다.
2. 각 유틸리티가 `serviceType`을 `switch`하여 해당 Connection Schema를 반환한다.
3. `ConnectionConfigForm`이 기본 필터 필드를 분리하고 `schema`와 `uiSchema`를 준비한다.
4. `FormBuilder`가 RJSF와 AJV validator로 입력 UI를 렌더링하고 값을 검증한다.

```typescript
case ServiceCategory.DATABASE_SERVICES:
  connSch = serviceUtilClassBase.getDatabaseServiceConfig(
    serviceType as DatabaseServiceType
  );
```

```tsx
<FormBuilder
  schema={schemaWithoutDefaultFilterPatternFields}
  uiSchema={uiSchema}
  validator={validator}
/>
```

새 커넥터의 Connection Schema 파일만 추가하면 화면에 자동으로 나타나는 구조는 아니다. 먼저 서비스 엔티티 Schema의 type enum에 등록해 `SelectServiceType` 목록에 포함하고, 해당 서비스 계열의 `serviceType` 분기에서 Form용 Schema를 선택하도록 연결해야 한다.

## 3. Theme & 브랜딩

Theme 설정은 저장된 색상·브랜드 자산을 앱 시작 시 불러와 서로 다른 UI 계층에 전달한다. 설정값의 저장 구조와 실제 적용 경로를 분리해 볼 필요가 있다.

### 3.1 Theme에서 설정하는 값

**UI 페이지:** `Settings > Preferences > Theme`

| 설정 그룹 | 대표 필드 | 적용 대상 |
|---|---|---|
| 기본 강조색 | `primaryColor` | 버튼, 링크, 강조 요소 |
| 상호작용 상태 | `hoverColor`, `selectedColor` | hover·선택 상태 |
| 의미 색상 | `errorColor`, `successColor`, `warningColor`, `infoColor` | 오류·성공·경고·정보 상태 |
| 패널 배경 | `panelBackgroundColor` | Landing Page welcome panel의 기본 배경색 |
| 브랜드 자산 | logo, monogram, favicon 경로 | 헤더·로그인·브라우저 아이콘 |

### 3.2 설정 데이터의 저장과 초기화

`uiThemePreference.json`은 색상 설정인 `customTheme`과 이미지 경로 설정인 `customLogoConfig`를 함께 정의한다. 두 값은 같은 Preference에 저장되지만 적용 방식은 다르다.

- `customTheme`은 `getThemeConfig()`에서 비어 있는 기본·상태·의미 색상을 기본값으로 보완한 뒤 `applicationConfig`에 저장된다.
- `customLogoConfig`는 favicon과 화면별 logo·monogram 경로를 선택할 때 사용된다.

`AppRoot`가 Theme Preference와 시스템 설정을 함께 읽고 전역 Store를 초기화한다.

```typescript
setApplicationConfig({
  ...themeData,
  customTheme: getThemeConfig(themeData.customTheme),
});
```

`getThemeConfig()`의 역할은 palette 생성이 아니라 누락된 기본·상태·의미 색상을 기본 Theme로 보완하는 것이다. `panelBackgroundColor`는 optional 값으로 유지되며, 실제 palette와 CSS 변수는 각 UI Provider에서 만든다.

### 3.3 설정값이 화면에 도달하는 경로

`applicationConfig.customTheme`은 현재 앱에 공존하는 세 UI 계층에 전달된다.

| 적용 경로 | 처리 |
|---|---|
| `AntDConfigProvider` | `primaryColor`로 palette를 만들고 Ant Design Theme와 `--ant-*` CSS 변수에 반영 |
| MUI `ThemeProvider` | 공유 패키지의 `createMuiTheme()`으로 MUI Theme 생성 |
| `UntitledUIThemeProvider` | 브랜드·상태 색상을 Tailwind의 `--tw-*` CSS 변수에 반영 |

![설정값이 화면에 도달하는 경로](발표자료-assets/theme-flow.svg)

Ant Design에서는 저장된 `hoverColor`를 `--ant-primary-1`에, `selectedColor`를 `--ant-primary-7`과 active 상태에 매핑한다. 값이 없으면 `primaryColor`로 만든 palette를 사용하며, `--ant-primary-color-hover`는 별도로 `palette[6]`을 사용한다.

```typescript
const palette = generatePalette(
  applicationConfig?.customTheme?.primaryColor ?? DEFAULT_THEME.primaryColor
);
const hoverColor =
  applicationConfig?.customTheme?.hoverColor ||
  palette[2] ||
  DEFAULT_THEME.hoverColor;
const selectedColor =
  applicationConfig?.customTheme?.selectedColor ||
  palette[8] ||
  DEFAULT_THEME.hoverColor;
```

## 4. Persona 기반 개인화

Persona는 사용자의 직무·업무 유형별 UI 구성을 연결하는 엔티티다. RBAC 권한을 정의하는 Role과는 별개이며, 로그인 사용자의 기본 Persona, 현재 선택된 Persona, Persona별 문서가 이어져 Navigation과 Page 구성을 결정한다.

### 4.1 Persona 개인화 흐름

**UI 페이지:** `Settings > Personas`

사용자의 `defaultPersona`는 로그인 직후 선택값을 정한다. 이후 화면은 현재 Store의 `selectedPersona`를 기준으로 `persona.<FQN>` 문서를 조회하고, 그 문서에서 Navigation과 필요한 Page를 읽는다.

![Persona 개인화 흐름](발표자료-assets/persona-flow.svg)

### 4.2 기본 Persona와 현재 선택 Persona

`Persona.default`는 할당된 Persona나 사용자 기본값이 없을 때 서버가 적용하는 시스템 fallback이다. Frontend Store는 서버에서 받은 `User.defaultPersona`를 직접 사용해 현재 브라우저의 `selectedPersona`를 초기화한다.

```typescript
const { defaultPersona } = user;
set({ currentUser: user, selectedPersona: defaultPersona });
```

이후 사용자가 Persona를 바꾸면 `selectedPersona`가 변경되고, 이를 구독하는 화면이 새 Persona의 문서를 다시 조회한다.

### 4.3 Persona 문서에서 Page와 Navigation 조회

`useCustomPages(pageType)`는 선택 Persona의 `fullyQualifiedName`으로 문서 FQN을 만든다. 조회된 문서의 `pages`에서는 요청한 `pageType` 하나를 선택하고, `navigation`은 별도 상태로 저장한다.

```typescript
const pageFQN =
  `${EntityType.PERSONA}${FQN_SEPARATOR_CHAR}${selectedPersona?.fullyQualifiedName}`;
const doc = await getDocumentByFQN(pageFQN);

setCustomizedPage(doc.data?.pages?.find((p) => p?.pageType === pageType));
setNavigation(doc.data?.navigation);
```

Persona 이름을 화면 코드의 조건문으로 비교하는 방식이 아니라, 선택 Persona에 연결된 문서 데이터를 같은 렌더러가 읽는 구조다.

`useCustomPages`는 선택 Persona가 없으면 문서를 조회하지 않고 loading만 종료한다. 문서 조회에 실패한 경우에는 `navigation=[]`, `customizedPage=null`로 초기화한다. Landing Page의 별도 fallback은 5장에서 다룬다.

## 5. 커스터마이즈 가능한 Landing Page

앞 절에서 조회한 Persona 문서의 `pages` 중 `pageType`이 `LandingPage`인 항목이 시작 화면 구성을 담는다. 편집 화면과 실제 Home 화면은 같은 `layout` 데이터를 사용한다.

### 5.1 Landing Page 구성 데이터

**설정 UI 페이지:** `Settings > Personas > <Persona> > Customize UI > Landing Page`

**렌더링 UI 페이지:** `Home / My Data`

Landing Page의 `Page.layout`은 `WidgetConfig[]`로 사용된다. 각 항목은 위젯의 종류와 grid 배치를 함께 기록한다.

| 필드 | 의미 |
|---|---|
| `i` | grid에서 사용하는 고유 ID이자 위젯 종류를 찾는 키 |
| `x`, `y` | grid 안의 시작 좌표 |
| `w`, `h` | 위젯의 너비와 높이 |
| `static`, `isDraggable` | 이동 가능 여부 |
| `config`, `children` | 위젯별 추가 설정과 하위 구성 |

`i`에는 `KnowledgePanel.ActivityFeed`, `KnowledgePanel.KPI`, `KnowledgePanel.MyTask` 같은 값이 들어간다. 저장된 좌표와 크기에 따라 같은 위젯을 다른 위치와 크기로 렌더링할 수 있다.

### 5.2 하나의 Layout을 편집하고 다시 렌더링한다

편집 화면은 `react-grid-layout`의 `data-grid`에 각 `WidgetConfig`를 전달한다. 현재 grid는 resize를 비활성화하고, 드래그 이동·위젯 추가·제거로 바뀐 배열을 저장해 Persona의 Landing Page 데이터를 갱신한다. 위젯 너비는 추가할 때 선택한 `widgetSize`로 정한다.

`Home / My Data`는 선택 Persona의 문서를 다시 조회하고 같은 `layout`을 순회한다. 편집 전용 화면을 캡처해 저장하는 것이 아니라, 저장된 좌표와 위젯 ID를 실제 화면에서 다시 해석한다.

선택 Persona가 없거나 문서 조회에 실패하거나 저장된 `layout`이 비어 있으면 `CustomizeMyDataPageClassBase`의 `defaultLayout`을 사용한다. 기본 layout에는 Activity Feed, Data Assets, My Data, KPI, Total Assets, Following이 들어 있다.

![하나의 Layout을 편집하고 다시 렌더링한다](발표자료-assets/landing-layout-flow.svg)

### 5.3 위젯 ID와 React 컴포넌트 연결

`WidgetConfig.i`는 React Grid Layout의 key로 사용되는 동시에 실제 위젯 컴포넌트를 찾는 값이다.

```tsx
layout.map((widget) => (
  <div data-grid={widget} key={widget.i}>
    {getWidgetFromKey({ widgetConfig: widget, currentLayout: layout })}
  </div>
));
```

`getWidgetFromKey()`는 `widgetConfig.i`를 `getWidgetsFromKey()`에 전달해 Activity Feed, KPI, My Task 같은 React 컴포넌트를 선택한다.

```typescript
const Widget =
  customizeMyDataPageClassBase.getWidgetsFromKey(widgetConfig.i);
```

따라서 위젯 구현과 Persona별 배치 데이터는 분리된다. 같은 컴포넌트를 사용하면서 Persona마다 포함할 위젯과 위치·크기를 다르게 구성할 수 있다.
