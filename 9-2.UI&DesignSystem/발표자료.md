## 1. Frontend 빌드 체계

OpenMetadata UI는 브라우저에서 실행되는 React 애플리케이션, 이를 보조하는 공유 UI 패키지, 개발 환경을 준비하는 Node·Yarn, 그리고 화면과 타입의 기준이 되는 JSON Schema가 함께 구성한다. 먼저 각 요소가 어디에 있고 어떤 결과를 만드는지 정리한 뒤, 다음 절에서 Service 연결 화면이 이 구조를 어떻게 사용하는지 본다.

### 1.1 Frontend 소스 구조

`openmetadata-ui/src/main/resources/ui/src`는 실제 화면을 실행하는 애플리케이션의 소스 루트다. 폴더는 화면, 재사용 UI, 상태·컨텍스트, API 호출, Schema 산출물처럼 역할에 따라 나뉜다.

```text
src/
├── pages/                  URL에 대응하는 업무 화면
├── components/             화면 안에서 조합하는 도메인·공통 UI
├── context/ · hooks/       인증·Theme·사용자 선택값 같은 공유 상태와 동작
├── rest/                   OpenMetadata Server REST API 호출
└── generated/ · jsons/     Schema에서 준비한 TypeScript 타입과 Form용 JSON
```

- `pages`는 URL에 대응하는 화면 단위다. Service 추가, Theme, Persona, My Data 같은 업무 화면이 이 계층에서 시작한다.
- `components`는 여러 화면에서 조합하는 도메인·공통 UI다. `pages`가 화면의 진입점이라면 `components`는 화면 안의 기능 단위다.
- `context`, `hooks`는 인증, Theme, 사용자 선택값처럼 여러 화면이 공유하는 상태와 동작을 연결한다.
- `rest`는 OpenMetadata Server API 호출을, `generated`와 `jsons`는 JSON Schema에서 준비한 타입·Form용 JSON을 담당한다.

위 트리는 정적인 책임 구분이다. 실제 시작 순서는 `index.tsx → AppRoot → App / AuthProvider / AppRouter → AuthenticatedApp → AuthenticatedRoutes → AppContainer → pages`다. 즉, 공통 설정과 인증을 먼저 준비한 뒤 실제 업무 화면을 표시한다.

![Frontend 실행 흐름](발표자료-assets/frontend-build-flow.svg)

### 1.2 `openmetadata-ui-core-components` 구조

`openmetadata-ui-core-components`는 앱과 별도로 빌드되는 공유 UI 패키지다. 반복 사용되는 Button·Input·Table 같은 컴포넌트와 색상·Theme·스타일 규칙을 한 곳에서 제공한다. 앱 전체를 대체하는 프레임워크가 아니라, 여러 화면이 같은 UI 기반을 쓰도록 만드는 공통 계층이다.

```text
src/
├── components/
│   ├── base/               Button, Input, Select 같은 기본 구성요소
│   ├── application/        Table, Modal, DatePicker 같은 조합 구성요소
│   └── foundations/        디자인 토큰을 반영한 기반 구성요소
├── theme/ · colors/        createMuiTheme, palette·색상 유틸리티
├── styles/                 Tailwind tw: 접두사와 공통 스타일
├── utils/ · types/ · hooks/ 공유 유틸리티, 타입, Hook
└── index.ts                앱이 import하는 공개 API
```

`src/index.ts`가 `components`, `theme`, `colors`, `utils`, `types`를 공개 API로 다시 export한다. 앱은 내부 파일 경로가 아니라 패키지 import를 통해 이 API를 사용한다.

```typescript
import { Button, createMuiTheme } from '@openmetadata/ui-core-components';
```

저장소 폴더명은 `openmetadata-ui-core-components`, 앱에서 사용하는 패키지명은 `@openmetadata/ui-core-components`다. 현재 저장소에 `openmetadata-ui-components`라는 별도 패키지는 없다.

### 1.3 UI 라이브러리가 공존하는 이유

현재 UI는 하나의 라이브러리로 만들어지지 않았다. Ant Design과 MUI는 범용 UI 라이브러리고, `@openmetadata/ui-core-components`는 이 프로젝트에서 공통으로 쓰기 위해 만든 UI 패키지다. 아래 표는 각 도구가 **어디에 쓰이는지**, **Theme 색상을 어떻게 받는지**, **새 코드를 작성할 때 무엇을 선택할지**를 비교한다.

| 도구 | 어디에 쓰이나 | 색상 변경은 어떻게 반영되나 | 새 컴포넌트를 만들 때 |
|---|---|---|---|
| Ant Design | 기존 화면의 Form, Table, 기본 버튼·입력 UI | 설정 색상을 Ant Design의 버튼·입력·선택 상태에 전달한다. | 기존 Ant Design 화면을 고칠 때는 그 화면의 방식을 유지한다. 다른 라이브러리로 바꾸지 않는다. |
| MUI | MUI를 사용하는 일부 공통 컴포넌트 | 만든 Theme 객체를 MUI 컴포넌트에 전달한다. | MUI 컴포넌트가 필요하면 프로젝트의 `createMuiTheme()`을 사용한다. |
| `@openmetadata/ui-core-components` | 새로 만드는 Button·Input 같은 범용 공유 UI와 디자인 토큰 | 설정 색상을 새 공유 UI의 CSS 변수에 넣어 사용한다. | 새 범용 공유 컴포넌트는 이 패키지의 컴포넌트·토큰을 우선 사용한다. |

`AppRoot`는 하나의 `customTheme`을 `applicationConfig`에 보관하지만, 각 라이브러리는 위와 같이 다른 Provider와 token으로 이를 소비한다. 이 때문에 기존 화면과 새 공유 UI가 공존해도 같은 강조색·상태색 기준을 유지한다.

공유 패키지의 컴포넌트 기반은 MUI나 Ant Design 자체가 아니라 `react-aria-components`와 Untitled UI 패턴이다. 스타일은 Tailwind의 `tw:` 접두사와 디자인 토큰을 사용해 기존 Ant Design·Less 스타일과 충돌하지 않게 한다. 따라서 새 공유 컴포넌트를 만들 때는 Ant Design이나 MUI 스타일을 직접 섞기보다, 패키지의 컴포넌트·토큰·접근성 기반을 따르는 것이 저장소의 개발 기준이다.

### 1.4 Node·Yarn과 개발 서버

Node.js는 브라우저 화면을 대신 실행하는 환경이 아니다. 개발자가 Vite 같은 JavaScript 기반 도구를 실행하는 런타임이다. React 화면 자체는 Vite가 제공한 파일을 브라우저가 실행한다.

| 도구 | 이 자료에서의 역할 |
|---|---|
| Node.js | Vite를 포함한 Frontend 개발 도구가 실행되는 런타임이다. |
| Yarn | 필요한 패키지를 설치하고, 프로젝트가 정의한 개발 명령을 실행한다. |
| Vite | `yarn start`로 개발 서버를 열고, 변경한 Frontend 코드를 브라우저에 제공한다. |

개발 시작은 다음 흐름으로 이해하면 충분하다.

1. `make yarn_install_cache`가 앱 UI와 공유 UI 패키지에 필요한 의존성을 준비한다.
2. `make yarn_start_dev_ui`가 앱의 `yarn start`, 즉 Vite 개발 서버를 실행한다.
3. 브라우저가 개발 서버에서 받은 React 코드를 실행하고, 파일 변경을 화면에 반영한다.

```bash
make yarn_install_cache
make yarn_start_dev_ui
```

### 1.5 JSON Schema: JSON 데이터의 계약

JSON Schema는 “어떤 JSON을 유효한 데이터로 볼 것인가”를 선언하는 형식이다. 특정 화면이나 프로그래밍 언어에 묶이지 않으며, 데이터의 형태와 검증 규칙을 함께 적는 계약이다. OpenMetadata에서는 이 계약을 기준으로 타입을 만들고, Service 연결 화면은 필요한 입력 구조를 읽는다.

JSON 값과 JSON Schema는 구분해야 한다. 연결 설정 값은 `{"hostPort":"db:3306"}`처럼 실제 입력 데이터이고, Schema는 `hostPort`가 string이어야 한다는 규칙이다. Schema는 세 가지 역할을 함께 한다.

- **구조 정의:** 필드 이름, 자료형, 중첩 object·array 구조를 정한다.
- **검증 기준:** 필수 값, 허용 선택지, 인증 방식처럼 유효한 입력 범위를 정한다.
- **공유 기준:** 공통 인증·SSL 규칙을 `$ref`로 재사용하고, 생성된 타입과 Form이 같은 필드 구조를 보게 한다.

| Schema 키워드 | 의미 | Connection 설정에서의 예 |
|---|---|---|
| `type` | 값의 기본 형태 | `string`, `boolean`, `object` |
| `properties` | object 안에 둘 필드 | `hostPort`, `username`, `authType` |
| `required` | 반드시 받아야 할 필드 | `hostPort`, `username` |
| `enum`, `default` | 제한된 선택지와 기본값 | Service Type, Connection Scheme |
| `oneOf` | 여러 구조 중 하나를 선택 | Basic·IAM 등 인증 방식 |
| `$ref` | 다른 Schema의 공통 정의를 참조 | SSL, 인증, Filter Pattern |

MySQL Connection Schema는 이 규칙을 실제로 사용한다. `authType`의 각 선택지는 별도 인증 Schema를 참조하고, 필수 항목은 `required`에서 한 번에 선언한다.

```json
"authType": {
  "oneOf": [
    { "$ref": "./common/basicAuth.json" },
    { "$ref": "./common/iamAuthConfig.json" }
  ]
},
"required": ["hostPort", "username"]
```

OpenMetadata에서 원본 Schema는 `openmetadata-spec`에 있고, 한 정의가 두 방향으로 사용된다.

| 결과 | 목적 | Frontend에서의 위치 |
|---|---|---|
| TypeScript 타입 | API 요청·응답과 props가 같은 필드 구조를 사용하게 하는 정적 타입 | `src/generated` |
| Form용 JSON asset | 브라우저가 Service별 입력 필드와 기본 검증 규칙을 읽게 하는 runtime 데이터 | `src/jsons/connectionSchemas` |

`quicktype`은 첫 번째 TypeScript 타입만 만든다. Form용 JSON은 브라우저가 읽는 별도 asset이며, 공통 Schema 참조를 Form에서 사용할 수 있는 형태로 준비한다. 따라서 Schema가 필드의 구조·검증을 정의해도 화면 전체가 자동으로 결정되지는 않는다. 다음 절의 UI는 `uiSchema`, custom field, 별도 필터 단계로 표시 순서와 추가 동작을 보완한다.

## 2. 커넥터 UI 통합 패턴

1절의 JSON Schema가 실제 화면에서 쓰이는 대표 사례가 Service 추가 화면이다. 이 절은 선택한 제품이 입력 Form으로 바뀌고, 사용 중인 필드의 문서까지 함께 따라오는 과정을 다룬다.

### 2.1 Service는 외부 시스템의 연결 등록 단위

이 문맥의 Service는 일반적인 백엔드 마이크로서비스를 뜻하지 않는다. OpenMetadata가 메타데이터를 수집하거나 연결 설정을 보관할 외부 플랫폼의 등록 단위다. 하나의 Service에는 연결 방식과 그 아래에서 관리할 메타데이터 유형이 함께 정해진다.

| Service Category | Service Type 예시 | OpenMetadata가 연결하는 대상 |
|---|---|---|
| Database | MySQL, PostgreSQL | Database·Schema·Table 같은 데이터 자산 |
| Messaging | Kafka | Topic 같은 메시지 자산 |
| Dashboard | Superset | Dashboard·Chart 같은 BI 자산 |

`serviceCategory`는 Database·Messaging처럼 큰 계열을 고르고, `serviceType`은 MySQL·Kafka·Superset처럼 구체적인 제품을 고른다. 이 두 값이 어떤 Connection Schema와 Form을 읽을지 결정한다.

### 2.2 Service 선택이 연결 설정 Form이 되는 과정

**UI 페이지:** `Settings > Services > Add New Service`

Service 추가는 네 단계로 진행한다. 이 중 **연결 설정** 단계에서 선택한 Service Type의 JSON Schema가 Form의 필드·필수값·선택지를 결정한다. 예를 들어 MySQL을 선택하면 MySQL 연결 설정 Schema의 `hostPort`, 인증 방식, SSL 관련 규칙을 읽어 입력 UI를 만든다.

| 단계 | 화면에서 정하는 값 | 다음 단계에 주는 정보 |
|---|---|---|
| Service 선택 | `serviceCategory`, `serviceType` | 선택할 Connection Schema의 기준 |
| 기본 정보 | Service 이름·설명 | OpenMetadata에 등록할 Service 정보 |
| 연결 설정 | host, 인증 방식, 옵션 등 | 선택 Schema에 맞는 연결 값 |
| 필터 설정 | 포함·제외 패턴 | 수집 대상을 제한하는 규칙 |

브라우저는 먼저 `serviceCategory`로 Service 계열의 설정 유틸리티를 고르고, 그 안에서 `serviceType`으로 구체적인 JSON Schema를 찾는다. `ConnectionConfigForm`은 이 결과에서 연결 Form에 필요한 `schema`와 `uiSchema`를 꺼내 `FormBuilder`에 전달한다. `FormBuilder`는 RJSF가 입력 UI를 만들고 AJV validator가 Schema 규칙을 검사하도록 연결한다.

`schema`가 **무슨 필드와 어떤 값이 가능한지**를 정한다면, `uiSchema`는 **어떤 필드를 숨기고 어떤 입력 위젯·순서로 보일지**를 보완한다. 그래서 JSON Schema만으로 Form의 데이터 계약을 유지하면서도, 연결 화면에 맞는 표시 규칙을 추가할 수 있다.

![Service 선택부터 Form·문서까지의 흐름](발표자료-assets/connector-ui-flow.svg)

### 2.3 Category `switch`와 Type `switch`의 역할

연결 Schema를 찾는 `switch`는 두 층이다. 둘을 구분하지 않으면 새 커넥터를 등록할 때 어느 위치를 고쳐야 하는지 알기 어렵다.

| 구분 | 기준 값 | 하는 일 | 예: MySQL |
|---|---|---|---|
| 1차 분기 | `serviceCategory` | Database·Messaging 같은 큰 계열에 맞는 설정 유틸리티를 선택한다. | `DATABASE_SERVICES` → Database 설정 유틸리티 |
| 2차 분기 | `serviceType` | 그 계열 안에서 제품별 JSON Schema asset을 선택한다. | `Mysql` → `mysqlConnection` |

```typescript
// 1차: 어느 Service 계열의 설정 유틸리티를 쓸지 결정
case ServiceCategory.DATABASE_SERVICES:
  return getDatabaseServiceConfig(serviceType);

// 2차: Database 안에서 어느 제품 Schema를 쓸지 결정
case DatabaseServiceType.Mysql:
  schema = mysqlConnection;
  break;
```

따라서 Database 계열에 MySQL과 PostgreSQL을 추가하는 일은 대체로 같은 1차 경로를 지나고, 2차 분기에서 서로 다른 Schema를 고르는 일이다. 새 **제품**을 기존 계열에 넣을 때는 Type enum·제품 Schema import·해당 계열 유틸리티의 Type 분기를 맞춘다. 새 **계열**을 만들 때에만 `ServiceConnectionUtils`의 1차 Category 분기도 추가한다.

이 연결점이 맞아야 선택 화면의 제품명, runtime Form의 입력 구조, API로 저장할 연결 값이 모두 같은 Service를 가리킨다. JSON 파일만 놓거나 `switch`만 추가하면 한 단계가 끊겨 선택 목록·Form·저장 데이터 중 일부가 어긋날 수 있다.

### 2.4 Follow-along 문서: 입력 위치에 맞춰 설명을 이동한다

**UI 페이지:** `Settings > Services > Add New Service`

연결 설정 단계는 왼쪽에 입력 Form을, 오른쪽에 선택한 Service의 안내 문서를 함께 표시한다. 이것은 발표 자료의 참고 문서 목록이 아니라, 실제 제품 안에서 사용자가 입력 중인 항목의 설명을 바로 찾게 하는 UI 기능이다.

동기화의 기준은 필드 이름이다. 사용자가 `hostPort` 입력란을 focus하면 Form이 `activeField=hostPort`를 전달하고, `ServiceDocPanel`은 현재 언어와 선택된 Service의 Markdown을 읽는다. Markdown 처리 단계는 `$(id="hostPort")`가 포함된 `$$section`을 `data-id="hostPort"`를 가진 HTML section으로 바꾼다. 마지막으로 패널은 같은 `data-id`를 찾아 해당 문단으로 스크롤하고 강조한다.

```typescript
// Form focus → activeField → 문서의 같은 data-id section
const fieldName = getActiveFieldName(activeField);
document.querySelector(`[data-id="${fieldName}"]`)?.scrollIntoView();
```

문서 작성 시의 최소 단위는 다음처럼 Form property 이름과 문서 ID를 같게 두는 것이다.

```markdown
$$section
$(id="hostPort")
호스트와 포트를 입력한다.
$$
```

이 연결은 “문서가 존재한다”만으로는 완성되지 않는다. 새 커넥터에서는 다음 세 계약을 함께 확인한다.

1. Connection Schema의 property 이름이 예를 들어 `hostPort`인지 확인한다.
2. 해당 Service·언어 경로의 Markdown 파일에 같은 `$(id="hostPort")` section을 둔다.
3. Form의 field focus가 전달한 이름과 문서 section의 `data-id`가 일치하는지 확인한다.

ID가 다르면 Form 입력 자체는 동작하지만 우측 문서는 이동·강조되지 않는다. 번역 문서가 없을 때는 영어 Markdown으로 fallback한다. 즉, Follow-along 문서는 Schema의 필드명과 문서의 설명을 같은 키로 묶어, 사용자가 현재 입력 중인 항목을 기준으로 문서를 읽게 만드는 기능이다.

## 3. Theme & 브랜딩 커스터마이징

Theme는 색상만 바꾸는 기능이 아니다. 하나의 Preference에서 만든 값이 기존 Ant Design 화면, MUI 기반 UI, 새 공유 UI의 token으로 나뉘어 전달되고, 브랜드 이미지는 별도 경로로 적용된다.

### 3.1 Theme에서 조정하는 값

**UI 페이지:** `Settings > Preferences > Theme`

| 설정 그룹 | 대표 필드 | 사용자가 보는 영역 |
|---|---|---|
| 기본 강조색 | `primaryColor` | 주요 Button·Link, Navigation·Tab의 강조 기준 |
| 상호작용 상태 | `hoverColor`, `selectedColor` | Button hover, Navigation·Tab·목록의 hover와 선택 상태 |
| 의미 색상 | `errorColor`, `successColor`, `warningColor`, `infoColor` | 오류·성공·경고·정보 상태 |
| 패널 배경 | `panelBackgroundColor` | Landing Page welcome header의 기본 배경색 |
| 브랜드 자산 | logo, monogram, favicon 경로 | 로그인 Logo, 좌측 Navigation monogram, 브라우저 탭 아이콘 |

여기서 `primaryColor`가 모든 header 배경을 같은 색으로 칠하는 값은 아니다. Navigation·Tab·Button처럼 강조 또는 선택 상태를 가진 컴포넌트가 Provider를 통해 이 색상 계열을 소비한다. Landing Page header 배경은 `panelBackgroundColor`를 우선 사용하고, Persona의 Landing 설정이 별도 header 색상을 가지고 있으면 그 값으로 덮어쓴다.

### 3.2 하나의 Preference를 여러 UI 계층에 적용한다

`uiThemePreference.json`은 색상 설정 `customTheme`과 이미지 경로 설정 `customLogoConfig`를 함께 저장한다. 앱 시작 시 `AppRoot`가 이 Preference를 읽어 `applicationConfig`에 둔다.

```typescript
setApplicationConfig({
  ...themeData,
  customTheme: getThemeConfig(themeData.customTheme),
});
```

`getThemeConfig()`은 비어 있는 기본·상태·의미 색상을 보완한다. 그 결과 `customTheme`을 각 Provider가 자신이 이해하는 palette 또는 CSS 변수로 바꾼다. 같은 Preference가 세 계층에 닿지만, 실제 적용 방법은 아래처럼 다르다.

| UI 계층 | Theme를 전달하는 방식 | 주로 달라지는 화면 |
|---|---|---|
| 기존 Ant Design | `AntDConfigProvider`가 palette와 `--ant-*` 변수를 만들고 `ConfigProvider`에 전달 | 기존 Form·Table·Button, Navigation·Tab의 강조·hover·선택 상태 |
| MUI 기반 컴포넌트 | `createMuiTheme()` 결과를 MUI `ThemeProvider`에 전달 | MUI를 사용하는 공통 컴포넌트의 color palette·상태색 |
| 새 공유 UI | `UntitledUIThemeProvider`가 `--tw-color-brand-*` CSS 변수를 생성 | `@openmetadata/ui-core-components`의 Button·Input 등 새 공유 UI |

예를 들어 Ant Design 쪽은 primary·hover·selected 값을 palette의 기본색, hover 상태, active 상태로 나누어 Button과 Navigation·Tab 같은 기존 컴포넌트에 제공한다. 새 공유 UI는 같은 브랜드 값을 `--tw-color-brand-600` 같은 token으로 읽는다. 따라서 새 UI에 CSS 색상을 직접 적는 대신 Provider token을 쓰면 Theme 화면의 변경이 해당 컴포넌트까지 이어진다.

`customLogoConfig`는 색상 token과 다른 경로다. `BrandImage`가 로그인 Logo와 Navigation monogram을 읽고, `AppRoot`가 favicon URL을 브라우저의 icon link에 적용한다. 여기서 Untitled UI는 별도 제품이 아니라 새 공유 UI가 쓰는 디자인 token 계층이다.

![설정값이 화면에 도달하는 경로](발표자료-assets/theme-flow.svg)

이 구조 때문에 Theme 화면 하나에서 설정해도 기존 화면의 Button·Navigation·Tab, MUI 컴포넌트, 새 공유 UI, Logo·favicon이 각각 맞는 방식으로 갱신된다.

## 4. Persona 기반 개인화

Persona는 사용자의 직무나 업무 유형에 맞춰 Navigation과 Page 구성을 선택하는 엔티티다. 조직은 Data Engineer, Data Steward, Data Scientist처럼 직무별 Persona를 정의할 수 있다. 이 이름들은 제품에 고정된 권한 묶음이 아니라, 조직이 화면 구성의 기준으로 만드는 업무 단위다.

| 구분 | 결정하는 것 | 예 |
|---|---|---|
| Role | 사용자가 할 수 있는 작업과 접근 권한 | 편집·관리·조회 가능 여부 |
| Persona | 사용자가 우선 보는 Navigation·Landing·Custom Page | Data Engineer용 시작 화면, Data Steward용 Navigation |

따라서 Persona를 바꿔도 Role 권한이 바뀌는 것은 아니다. 같은 권한을 가진 사용자가 업무 맥락에 맞는 화면 구성을 전환하는 장치다.

### 4.1 Persona를 정의하고 사용자에게 매핑한다

**Persona 정의 UI:** `Settings > Personas > <Persona>`
**사용자 매핑 UI:** `Settings > Users > <사용자>`

먼저 Persona에 이름과 UI 구성을 정의한다. 그 다음 User에 이 Persona를 연결해야 실제 사람이 선택할 수 있다. 한 사용자는 여러 Persona를 가질 수 있고, 직접 할당한 Persona와 팀에서 상속받은 Persona 중 하나를 기본 Persona로 삼는다.

| User 필드 | 의미 | 화면에 미치는 역할 |
|---|---|---|
| `personas` | 사용자에게 직접 할당한 Persona 목록 | 사용자가 선택할 수 있는 Persona 후보 |
| `defaultPersona` | 사용자에게 지정한 기본 Persona | 로그인 후 처음 적용할 Persona |
| `inheritedPersonas` | 팀의 기본 Persona에서 상속받은 목록 | 사용자가 직접 지정하지 않아도 사용할 수 있는 후보 |

예를 들어 Data Engineer Persona와 Data Steward Persona를 각각 정의한 뒤, 겸업 사용자는 두 Persona를 모두 후보로 받게 할 수 있다. 사용자 설정에서는 `personas`를 여러 개 선택하고, 그중 하나를 `defaultPersona`로 지정한다. 팀 기본 Persona가 있는 경우에는 `inheritedPersonas`도 후보에 합쳐진다.

### 4.2 Persona 문서가 화면 구성을 보관한다

**UI 페이지:** `Settings > Personas`

Persona 자체는 직무 단위이고, 실제 화면 구성은 그 Persona의 문서에 저장된다. 문서에는 Navigation과 여러 Page 설정이 들어간다. Landing Page도 이 문서의 `pages` 중 `pageType=LandingPage`로 보관된다.

| 문서 데이터 | 화면에서의 결과 |
|---|---|
| `navigation` | 좌측 Navigation의 메뉴 구성 |
| `pages` | Persona별 Custom Page와 Landing Page 구성 |
| Landing Page의 `layout` | 위젯의 포함 여부·위치·크기 |

이 방식은 화면 코드에 `if (persona === 'Data Engineer')` 같은 조건을 늘리지 않는다. 렌더러는 선택된 Persona 문서를 읽고, 그 문서의 Navigation·Page 데이터를 적용한다.

![Persona 개인화 흐름](발표자료-assets/persona-flow.svg)

### 4.3 Persona 선택 후 UI가 자동으로 전환된다

**UI 위치:** 상단 사용자 메뉴의 Persona 선택

로그인 뒤 Frontend Store는 `User.defaultPersona`를 `selectedPersona`의 초기값으로 둔다. 사용자가 상단 사용자 메뉴에서 다른 Persona를 선택하면 이 값만 바꾼다.

```typescript
// 상단 사용자 메뉴에서 선택한 Persona를 현재 상태로 반영
setSelectedPersona(persona);
```

그 다음의 전환은 다음 순서로 자동으로 진행된다.

1. `selectedPersona`가 새 Persona로 변경된다.
2. Navigation과 Page를 사용하는 화면이 새 Persona FQN으로 문서를 다시 조회한다.
3. 문서의 `navigation`을 좌측 메뉴에, `pages`와 Landing `layout`을 현재 화면에 적용한다.

즉, 사용자가 메뉴별 설정을 다시 고르는 것이 아니라 Persona 선택 한 번으로 Navigation·Custom Page·Home / My Data의 Landing 구성이 함께 바뀐다.

### 4.4 Page와 Navigation은 같은 Persona 문서에서 읽는다

`useCustomPages(pageType)`는 선택 Persona의 `fullyQualifiedName`으로 `persona.<FQN>` 문서를 찾는다. 문서의 `pages`에서는 요청한 `pageType` 하나를 고르고, `navigation`은 별도 상태로 적용한다.

```typescript
const doc = await getDocumentByFQN(pageFQN);
setCustomizedPage(doc.data?.pages?.find((p) => p?.pageType === pageType));
setNavigation(doc.data?.navigation);
```

따라서 화면 코드가 Persona 이름을 조건문으로 비교하지 않는다. 같은 렌더러가 선택 Persona에 연결된 문서 데이터를 읽어 Page와 Navigation을 구성한다.

## 5. 커스터마이즈 가능한 Landing Page

Landing Page는 Persona 문서의 `pages` 중 `pageType=LandingPage`인 Page에 저장된다. 편집 화면의 배치를 캡처해 보관하는 방식이 아니라, 위젯 ID와 grid 좌표가 담긴 `layout`을 저장하고 실제 Home 화면이 다시 해석한다.

### 5.1 Pluggable Panel은 위젯을 조합하는 Layout 구조다

**설정 UI 페이지:** `Settings > Personas > <Persona> > Customize UI > Landing Page`

**렌더링 UI 페이지:** `Home / My Data`

여기서 Pluggable Panel은 외부 플러그인을 내려받는 기능이 아니다. Landing Page가 정해진 위젯 카탈로그에서 필요한 panel을 고르고, 추가·제거·재배치한 결과를 `layout` 데이터로 저장하는 구조다. 렌더러는 위젯 키를 React 컴포넌트에 연결하고, grid는 그 컴포넌트가 놓일 위치를 해석한다.

발표 범위의 주요 위젯은 다음과 같다.

| 위젯 | 화면에서 전달하는 정보 | 현재 Landing 구조에서의 위치 |
|---|---|---|
| Activity Feed | 최근 활동·피드 | grid panel |
| KPI | 요약 지표 | grid panel |
| My Tasks | 사용자 작업 | grid panel |
| Announcements | 공지 | Landing header 영역 |
| Recently Viewed | 최근 열어본 자산 | Landing header 영역 |

현재 Add Widget dialog는 Activity Feed·KPI·My Tasks처럼 grid에 넣는 panel을 선택한다. Announcements와 Recently Viewed도 Landing 관련 위젯 키로 정의되어 있지만, 현재 구현에서는 Add Widget 목록에서 제외되고 Landing header가 별도로 표시한다. 둘 모두 Landing 경험에 포함되지만, 저장·렌더링 경로가 같지는 않다.

### 5.2 `WidgetConfig`가 패널의 종류와 배치를 함께 저장한다

`Page.layout`은 `WidgetConfig[]`다. 각 항목은 어떤 위젯인지와 grid에서 어느 위치·크기로 표시할지를 함께 기록한다.

| 필드 | 의미 |
|---|---|
| `i` | grid의 고유 ID이자 위젯 종류를 찾는 키 |
| `x`, `y` | grid 안의 시작 좌표 |
| `w`, `h` | 위젯의 너비와 높이 |
| `static`, `isDraggable` | 이동 가능 여부 |
| `config`, `children` | 위젯별 추가 설정과 하위 구성 |

`i`에는 `KnowledgePanel.ActivityFeed`, `KnowledgePanel.KPI`, `KnowledgePanel.MyTask` 같은 위젯 키가 들어간다. `i`는 React Grid의 고유 ID이면서 어떤 React 컴포넌트를 보여줄지 결정하는 키다. 같은 Activity Feed라도 Data Engineer Persona에서는 첫 번째 열에, 다른 Persona에서는 제외하거나 다른 열에 둘 수 있다.

### 5.3 추가·제거·재배치는 Layout 데이터를 바꾼다

편집 화면은 `react-grid-layout`의 `data-grid`에 각 `WidgetConfig`를 전달한다. 현재 grid는 패널을 drag해서 이동할 수 있지만 resize는 비활성화되어 있다. 위젯 너비는 추가할 때 선택한 크기로 정한다.

| 편집 동작 | Layout에 남는 변화 |
|---|---|
| 위젯 추가 | 새 `WidgetConfig`와 위젯 키를 배열에 추가 |
| 위치 변경 | 해당 위젯의 `x`, `y` 좌표 갱신 |
| 추가 시 크기 선택 | `w`, `h` 값 설정 |
| 위젯 제거 | 해당 `i`를 가진 config 제거 |

저장 후 `Home / My Data`는 선택 Persona 문서에서 같은 `layout`을 다시 읽는다. 즉, 편집 화면의 스크린샷을 저장하는 것이 아니라 위젯 키와 좌표를 데이터로 저장하고, 실제 화면에서 다시 해석한다.

![하나의 Layout을 편집하고 다시 렌더링한다](발표자료-assets/landing-layout-flow.svg)

### 5.4 Persona별 기본 화면과 공통 fallback

Persona 문서의 Landing Page마다 다른 `layout`을 저장할 수 있으므로, Data Engineer·Data Steward·Data Scientist Persona가 서로 다른 기본 화면을 가질 수 있다. 사용자가 Persona를 전환하면 `Home / My Data`는 선택된 Persona의 문서를 다시 읽어 그 Persona의 `layout`을 사용한다.

저장된 Persona layout이 없거나 비어 있거나 문서 조회에 실패한 경우에만 `CustomizeMyDataPageClassBase.defaultLayout`을 대신 사용한다. 이 fallback에는 Activity Feed, Data Assets, My Data, KPI, Total Assets, Following이 들어 있다. 즉, `defaultLayout`은 공통 대체값이고, 실제 Persona별 기본 화면은 Persona 문서의 `Page.layout`이다.

### 5.5 위젯 키가 React 컴포넌트를 고른다

`WidgetConfig.i`는 React Grid Layout의 key이면서 실제 위젯 컴포넌트를 찾는 키다.

```tsx
layout.map((widget) => (
  <div data-grid={widget} key={widget.i}>
    {getWidgetFromKey({ widgetConfig: widget, currentLayout: layout })}
  </div>
));
```

`getWidgetFromKey()`는 `widgetConfig.i`를 `getWidgetsFromKey()`에 전달해 Activity Feed, KPI, My Task 같은 React 컴포넌트를 선택한다. 따라서 위젯 구현과 Persona별 배치 데이터는 분리되며, 같은 위젯을 사용하면서도 Persona마다 포함 여부와 위치를 다르게 설정할 수 있다.
