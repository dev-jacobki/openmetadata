## 1. Frontend 구조와 공유 컴포넌트

### 1.1 두 UI 프로젝트의 역할

저장소의 실제 공유 모듈명은 `openmetadata-ui-core-components`이며, 앱에서는 `@openmetadata/ui-core-components` 패키지로 가져온다. 이름이 비슷한 `openmetadata-ui-components`가 아니라 **core components**가 공용 디자인 시스템 레이어다.

| 구분 | 위치 | 책임 |
|---|---|---|
| 앱 UI | `openmetadata-ui/src/main/resources/ui` | 라우팅, Page, 도메인별 `components`, REST API, Store |
| 공유 UI | `openmetadata-ui-core-components/src/main/resources/ui` | Theme, colors, base components, application components, utilities |

공유 UI는 `Button`, `Input`, `Card`, `Table`, `Tabs`, `Navigation`처럼 여러 화면에서 반복되는 요소를 묶어 제공한다. 앱 UI는 이 요소를 조합해 서비스·엔티티·설정 화면의 업무 흐름을 구현한다.

```json
"@openmetadata/ui-core-components":
  "link:../../../../../openmetadata-ui-core-components/src/main/resources/ui"
```

![Frontend 구조와 공유 컴포넌트](발표자료-assets/frontend-build-flow.svg)

### 1.2 빌드 순서와 코드 진입점

앱의 `preinstall`은 공유 컴포넌트 패키지를 먼저 설치·빌드한다. 이후 앱 UI가 로컬 링크 패키지를 사용한다. 따라서 공유 Button이나 Theme API를 바꿨다면 앱 실행 전에 core components의 빌드 결과가 갱신되어야 한다.

```bash
make yarn_install_cache
make yarn_start_dev_ui
```

**핵심 코드 위치**

- 앱 시작·빌드: `openmetadata-ui/.../ui/package.json`
- 앱 화면: `openmetadata-ui/.../ui/src/pages`, `src/components`
- 공유 공개 API: `openmetadata-ui-core-components/.../ui/src/index.ts`
- 공유 컴포넌트 export: `openmetadata-ui-core-components/.../ui/src/components/index.ts`

## 2. JSON Schema와 커넥터 UI

**UI 페이지**

`Settings > Services > Add New Service`

### 2.1 Schema가 담당하는 범위

서비스 연결 설정은 `openmetadata-spec`의 JSON Schema에서 필드명, 자료형, 필수값, 참조 구조를 정의한다. `source_type`은 서비스 설정 UI가 어떤 연결 유형을 다루는지 식별하는 기준이다.

`json2ts.sh`는 전달받은 Schema 파일의 상대 경로를 유지한 채 `src/generated/` 아래에 TypeScript 파일을 만든다. 생성된 타입은 UI의 API 요청, 설정값 접근, 컴포넌트 props에서 같은 필드명을 사용하게 한다.

```bash
# json2ts.sh: 입력 Schema → 같은 상대 경로의 TypeScript 파일
quicktype -s schema "$tmp_schema_file" \
  -o "$output_file" --just-types
```

![Schema에서 타입과 서비스 UI까지](발표자료-assets/schema-type-flow.svg)

### 2.2 타입 생성과 Form 구성은 분리된다

`quicktype`이 만드는 것은 TypeScript 타입이다. 서비스 추가 화면에서 어떤 입력 컨트롤을 보여 줄지, `source_type`별 선택지를 어떻게 연결할지는 UI 코드가 맡는다. 따라서 새 연결 유형을 추가할 때는 다음 세 지점을 함께 본다.

1. **Schema**: 연결 속성과 참조 구조를 정의한다.
2. **생성 타입**: `src/generated/`에 반영된 이름·타입을 사용한다.
3. **서비스 설정 UI**: 선택된 `source_type`에 맞는 Form과 요청 본문을 연결한다.

**핵심 코드 위치**

- Schema: `openmetadata-spec/src/main/resources/json/schema/`
- 생성 스크립트: `openmetadata-ui/src/main/resources/ui/json2ts.sh`
- 생성 결과: `openmetadata-ui/src/main/resources/ui/src/generated/`

## 3. Theme & 브랜딩

**UI 페이지**

`Settings > Preferences > Theme`

### 3.1 저장 모델

`uiThemePreference.json`은 `customLogoConfig`와 `customTheme`을 묶어 관리한다. `customTheme`은 `themeConfiguration.json`을 참조하며, 색상 값은 UI 설정·서버 설정·생성 타입에서 동일한 구조를 유지한다.

| 설정 그룹 | 대표 필드 | 화면에서의 역할 |
|---|---|---|
| 기본 강조색 | `primaryColor` | 버튼, 링크, 내비게이션의 기준색 |
| 상호작용 상태 | `hoverColor`, `selectedColor` | hover·선택 상태의 색상 |
| 의미 색상 | `errorColor`, `successColor`, `warningColor`, `infoColor` | 오류·성공·경고·정보 상태 |
| 브랜드 자산 | logo, monogram, favicon | 헤더·로그인·브라우저 아이콘 |

### 3.2 설정값이 화면에 도달하는 경로

앱 시작 시 `AppRoot`가 UI Theme Preference를 읽어 `applicationConfig`에 저장한다. 이후 두 UI 계층이 같은 `customTheme`을 사용한다.

- `AntDConfigProvider`: `primaryColor`로 palette를 만들고 CSS 변수와 Ant Design 설정에 반영한다.
- `AuthenticatedApp`: core components의 `createMuiTheme()`와 MUI `ThemeProvider`에 Theme를 전달한다.
- `UntitledUIThemeProvider`: 브랜드 색상을 별도 UI 계층에도 전달한다.

```typescript
const palette = generatePalette(primaryColor);
const hoverColor = savedHoverColor || palette[2];
const selectedColor = savedSelectedColor || palette[8];
```

![Theme 설정의 런타임 반영](발표자료-assets/theme-flow.svg)

**핵심 코드 위치**

- 설정 화면: `src/pages/AppearanceConfigSettingsPage/`
- 초기 로드: `src/AppRoot.tsx`
- Ant Design 적용: `src/context/AntDConfigProvider/`
- 공유 MUI Theme: `openmetadata-ui-core-components/.../src/theme/`

## 4. Persona 기반 개인화

**UI 페이지**

`Settings > Personas`

### 4.1 Persona 선택 상태

Persona는 역할별 화면 구성을 위한 엔티티다. User에는 기본 Persona가 연결될 수 있고, 로그인 사용자 정보를 Store에 넣을 때 `defaultPersona`가 `selectedPersona`의 초기값이 된다. 이후 UI는 선택된 Persona 하나를 기준으로 페이지와 내비게이션 구성을 읽는다.

| 값 | 역할 |
|---|---|
| `User.defaultPersona` | 로그인 후 기본으로 선택할 Persona |
| `selectedPersona` | 현재 UI가 참조하는 Persona |
| `Persona.fullyQualifiedName` | Persona별 UI 문서를 찾는 식별자 |

```typescript
const { defaultPersona } = user;
set({ currentUser: user, selectedPersona: defaultPersona });
```

### 4.2 Persona별 페이지 구성 조회

`useCustomPages`는 `persona.<FQN>` 형식의 문서를 조회한 뒤, 요청한 `pageType`에 해당하는 Page와 Navigation을 분리한다. 즉 화면은 Persona 이름을 조건문으로 직접 비교하지 않고, 선택 Persona에 연결된 문서 구성을 읽는다.

```typescript
const pageFQN =
  `${EntityType.PERSONA}${FQN_SEPARATOR_CHAR}${selectedPersona?.fullyQualifiedName}`;
const doc = await getDocumentByFQN(pageFQN);
```

![Persona 선택과 페이지 구성 조회](발표자료-assets/persona-flow.svg)

**핵심 코드 위치**

- Persona Schema: `openmetadata-spec/.../entity/teams/persona.json`
- 선택 상태: `src/hooks/useApplicationStore.ts`
- 페이지 조회: `src/hooks/useCustomPages.ts`
- 문서 API: `src/rest/DocStoreAPI.ts`

## 5. 커스터마이즈 가능한 Landing Page

**설정 UI 페이지**

`Settings > Personas > <Persona> > Customize UI > Landing Page`

**렌더링 UI 페이지**

`Home / My Data`

### 5.1 하나의 Layout을 편집하고 다시 렌더링한다

Landing Page의 핵심 데이터는 `Page.layout`이다. 편집 화면은 `react-grid-layout`으로 위젯의 위치·크기·순서를 수정하고, 저장 시 변경된 layout을 Persona의 Page 데이터에 반영한다. 같은 layout은 `Home / My Data`에서 다시 읽혀 렌더링된다.

| 단계 | 처리 |
|---|---|
| 편집 | 위젯 추가·제거·드래그, grid 좌표 수정 |
| 저장 | 변경된 `WidgetConfig[]`를 Page의 `layout`에 저장 |
| 렌더링 | `getWidgetFromKey()`가 widget key를 실제 React 컴포넌트로 연결 |

```typescript
layout.map((widget) =>
  getWidgetFromKey({ widgetConfig: widget, currentLayout: layout })
);
```

![Landing Page 레이아웃의 편집과 렌더링](발표자료-assets/landing-layout-flow.svg)

### 5.2 위젯 구성의 의미

기본적으로 Activity Feed, KPI, Announcements, Tasks, Recently Viewed 같은 위젯을 배치한다. 여기서 **위젯 컴포넌트**와 **레이아웃 데이터**는 분리되어 있다. 위젯 구현을 바꾸지 않아도 Persona별 `layout`의 항목·위치·크기를 달리해 시작 화면을 구성할 수 있다.

**핵심 코드 위치**

- 편집 화면: `src/components/MyData/CustomizableComponents/CustomizeMyData/`
- Persona Page 저장: `src/pages/CustomizablePage/`
- Landing Page 렌더링: `src/pages/MyDataPage/MyDataPage.component.tsx`
- Widget key 매핑: `src/utils/CustomizableLandingPageUtils.tsx`
