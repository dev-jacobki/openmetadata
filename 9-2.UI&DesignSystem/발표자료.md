# 9회-2. UI & 디자인 시스템

> OpenMetadata의 UI가 **스키마 계약**, **전역 테마**, **Persona 기반 구성**으로 확장되는 방식을 이해한다.

## 이번 발표의 한 문장

OpenMetadata의 화면은 컴포넌트만으로 완성되지 않는다. JSON Schema가 데이터 계약을 만들고, Theme가 전역 표현을 정하며, Persona와 문서형 레이아웃이 역할별 화면을 조합한다.

## 학습 범위

| 구분 | 확인할 내용 | 핵심 질문 |
|---|---|---|
| UI 개발 구조 | React·TypeScript·Vite·Yarn, 생성 타입 | 화면과 서버 모델이 어떻게 같은 계약을 쓰는가? |
| Schema → Type | JSON Schema와 quicktype | 새 설정 필드는 UI에서 어떻게 안전하게 쓰이는가? |
| Theme | Logo·색상 설정, Store, Provider | Primary Color 변경이 왜 여러 컴포넌트에 반영되는가? |
| Persona | Persona, User, Default Persona | 같은 사용자가 역할에 따라 왜 다른 UI를 보는가? |
| Landing Page | Document, Page, widget layout | 화면 레이아웃을 코드 배포 없이 어떻게 바꾸는가? |

## 1. UI를 읽는 출발점: 화면보다 계약을 먼저 본다

프런트엔드 루트는 `openmetadata-ui/src/main/resources/ui`다. 현재 구조에서는 React와 TypeScript로 화면을 만들고, Vite가 개발 서버와 빌드를 담당한다. Ant Design과 MUI·UI Core Components가 함께 사용되며, 전역 상태는 Zustand store가 담당한다.

```text
openmetadata-spec / JSON Schema
            │
            ├─ quicktype → UI의 src/generated/*.ts
            ├─ jsonschema2pojo → Server Java model
            └─ Python model → Ingestion

React Page / Component ── REST API ── OpenMetadata Server
```

핵심은 UI가 임의의 TypeScript 인터페이스를 먼저 정의하지 않는다는 점이다. 엔티티와 설정의 원천 계약을 `openmetadata-spec`의 JSON Schema에 두고, 각 실행 영역에 필요한 모델을 생성한다. 이 구조 덕분에 설정 이름·필수 여부·허용 값이 서버와 UI에서 엇갈릴 가능성을 줄일 수 있다.

### 1.1 로컬 UI 실행 흐름

UI만 개발할 때도 OpenMetadata Server가 필요하다. 화면은 서버의 REST API를 통해 설정, 사용자, Persona, 문서 레이아웃을 읽기 때문이다.

```bash
# OpenMetadata 저장소 루트
make yarn_install_cache
make yarn_start_dev_ui
```

`DEV_SERVER_TARGET`을 지정하면 별도로 실행 중인 OpenMetadata Server를 개발 UI가 바라보게 할 수 있다. UI 폴더의 `package.json`에는 `start: vite`, `build: vite build`, `parse-schema` 등의 스크립트가 있다.

### 1.2 어디부터 추적할까

| 목적 | 먼저 볼 파일 | 다음으로 이어질 파일 |
|---|---|---|
| 화면 진입점 | `src/AppRoot.tsx` | `components/AppRouter/AuthenticatedApp.tsx` |
| 전역 상태 | `hooks/useApplicationStore.ts` | Theme·현재 사용자·선택 Persona |
| 설정 API | `rest/settingConfigAPI.ts` | Server Settings API |
| Persona API | `rest/PersonaAPI.ts` | Persona 화면과 User API |
| 개인화 페이지 | `hooks/useCustomPages.ts` | `rest/DocStoreAPI.ts`, `pages/MyDataPage` |

## 2. JSON Schema가 TypeScript 타입으로 이어지는 과정

### 2.1 Schema-first의 의미

예를 들어 Theme 설정은 아래 Schema에서 색상 이름, 형식, 필수 여부를 정의한다.

```json
// openmetadata-spec/.../configuration/themeConfiguration.json
{
  "properties": {
    "primaryColor": { "type": "string", "pattern": "^#...$|^$" },
    "hoverColor":   { "type": "string", "pattern": "^#...$|^$" },
    "selectedColor": { "type": "string", "pattern": "^#...$|^$" }
  }
}
```

`uiThemePreference.json`은 `customLogoConfig`와 `customTheme`을 참조한다. UI는 생성된 `UIThemePreference` 타입을 가져와 같은 필드명을 사용한다. 이때 설정 화면의 Form, REST 요청 본문, Zustand Store가 서로 다른 타입을 따로 관리하지 않는다.

### 2.2 quicktype 생성 경로

`json2ts.sh`는 전달받은 JSON Schema 파일마다 `quicktype -s schema ... --just-types`를 실행한다. 결과는 UI의 `src/generated/` 아래에 Schema와 같은 상대 경로로 만들어진다.

```text
openmetadata-spec/src/main/resources/json/schema/configuration/uiThemePreference.json
      │
      └─ json2ts.sh / quicktype
             │
             └─ openmetadata-ui/.../src/generated/configuration/uiThemePreference.ts
```

특정 Schema만 다시 만들 때는 저장소 루트에서 다음처럼 실행한다.

```bash
./generate_ts.sh \
  openmetadata-spec/src/main/resources/json/schema/configuration/uiThemePreference.json
```

### 2.3 새 connector 또는 `source_type`을 추가할 때

새 연결 유형의 Schema에는 일반적으로 `type` 또는 source type을 구분하는 enum, 연결 정보, 인증 방식, 추가 옵션을 정의한다. 그 Schema가 Server·Ingestion·UI에서 동일한 모델로 이어진다.

1. `openmetadata-spec/.../entity/services/connections/<영역>/`에 Schema를 추가·수정한다.
2. `title`, `javaType`, `type` enum, `$ref`, `required`를 계약에 맞게 정의한다.
3. 생성 타입을 갱신한다.
4. UI Form과 연결 선택 화면에서 생성 타입을 사용한다.
5. 실제 API 요청과 UI 유효성 검사를 확인한다.

여기서 `quicktype`은 화면을 자동으로 만들어 주는 도구가 아니다. **타입 계약을 생성**하므로, 새 source type에 맞는 Form·선택지·표시 규칙은 UI에서 별도로 연결해야 한다.

## 3. Theme: 저장된 설정이 Provider를 거쳐 모든 UI로 간다

Theme은 단순 CSS 파일 교체가 아니라 Settings에 저장된 구성 값이다. 관리자는 **Settings → Preferences → Theme**에서 로고·모노그램·favicon과 색상을 설정한다.

```text
Settings 화면
  → CustomUIThemePreference 저장
  → AppRoot가 설정을 읽음
  → useApplicationStore.applicationConfig 갱신
  → AntD / MUI / Untitled UI Provider에 전달
  → 버튼·탭·선택 상태·헤더 등에 반영
```

### 3.1 저장하는 값

| 범주 | 대표 필드 | 쓰임 |
|---|---|---|
| Brand | `customLogoUrlPath`, `customMonogramUrlPath`, `customFaviconUrlPath` | 로그인·내비게이션·브라우저 아이콘 |
| Primary | `primaryColor` | 기본 강조색, 버튼·내비게이션 등의 기반색 |
| Interaction | `hoverColor`, `selectedColor` | hover·선택 상태를 명시적으로 조정 |
| Semantic | `errorColor`, `successColor`, `warningColor`, `infoColor` | 상태와 알림의 의미 색상 |
| Landing | `panelBackgroundColor` | Landing Page 환영 패널의 기본 배경 |

모든 색상은 3자리 또는 6자리 hex(또는 빈 문자열)만 허용한다. 빈 문자열이면 `getThemeConfig()`가 기본 Theme 색상으로 채운다.

### 3.2 왜 palette를 따로 만드는가

`AntDConfigProvider`는 Primary Color를 `generatePalette()`에 전달해 여러 단계의 색상을 만든다. hover 또는 selected 색상을 따로 설정하지 않았다면 palette의 특정 단계를 사용한다. 이후 CSS Custom Property(`--ant-primary-*`)와 Ant Design ConfigProvider에 반영한다.

```typescript
const palette = generatePalette(primaryColor);
const hoverColor = savedHoverColor || palette[2];
const selectedColor = savedSelectedColor || palette[8];
```

따라서 Primary Color만 바꿔도 단색 하나만 치환되는 것이 아니라, hover·active·selection에 필요한 파생 색까지 일관되게 달라진다. 반대로 특정 상태색이 브랜드 가이드에 고정되어 있다면 해당 값을 별도로 지정할 수 있다.

### 3.3 Theme 코드 추적 순서

1. `pages/AppearanceConfigSettingsPage/AppearanceConfigSettingsPage.tsx`에서 Form 값을 `CustomUIThemePreference`로 저장한다.
2. `AppRoot.tsx`가 `getCustomUiThemePreference()`를 호출해 시작 시 설정을 읽는다.
3. `useApplicationStore.ts`가 `applicationConfig`와 정규화된 `theme`을 보관한다.
4. `AntDConfigProvider.tsx`가 palette·CSS variables를 적용한다.
5. `AuthenticatedApp.tsx`가 MUI Theme와 Untitled UI Provider에 같은 색상 구성을 전달한다.

## 4. Persona: 역할과 화면 구성을 연결하는 엔티티

Persona는 단순 권한 묶음이 아니다. `Data Engineer`, `Data Steward`, `Data Consumer`처럼 **업무 역할 관점의 UI 경험**을 표현하는 엔티티다. 권한은 Role·Policy가 결정하고, Persona는 사용자가 무엇을 먼저 보고 어떤 화면 구조를 사용할지 정한다.

| 모델 | 담당 역할 |
|---|---|
| `Persona` | 이름·설명·사용자 목록·기본 Persona·UI customization 참조 |
| `User.defaultPersona` | 로그인 후 기본으로 선택할 역할 |
| `selectedPersona` | 현재 UI가 기준으로 삼는 Persona |
| `UICustomization` / `Document` | Persona별 페이지·내비게이션·Landing layout 저장 |
| `PersonaPreferences` | 사용자가 기본 Persona 구성 위에서 적용하는 제한된 개인 선호 |

### 4.1 선택과 기본값

`useApplicationStore`는 현재 사용자를 저장할 때 `defaultPersona`를 `selectedPersona`로 설정한다. Persona를 전환하면 `useCustomPages()`가 `persona.<FQN>` 문서를 다시 조회해 해당 역할의 Page·Navigation을 가져온다.

```text
User 로그인
  → defaultPersona 선택
  → selectedPersona 변경
  → DocStore에서 persona.<FQN> 문서 조회
  → Landing Page / Navigation layout 반영
```

사용자가 여러 Persona를 가질 수 있어도 화면의 기준점은 한 번에 하나의 `selectedPersona`다. 그래서 역할 전환은 로그인 재시작이 아니라, 선택 Persona와 그 문서 레이아웃을 다시 읽는 과정이다.

### 4.2 권한과 Persona를 혼동하지 말자

| 구분 | Persona | Role·Policy |
|---|---|---|
| 해결하는 문제 | 역할에 맞는 화면·시작점 | 어떤 데이터와 기능에 접근할 수 있는가 |
| 대표 설정 | Landing Page, Navigation, Page layout | View·Edit·Delete 권한 |
| 예 | Data Steward 화면에서 거버넌스 위젯을 우선 배치 | 해당 사용자에게 Glossary 편집 권한 부여 |

Persona를 바꾼다고 권한을 우회할 수는 없다. 보이는 위젯이나 메뉴가 바뀌어도 서버의 권한 검사는 별도로 적용된다.

## 5. Landing Page: 코드에 고정되지 않은 위젯 레이아웃

Landing Page는 `PageType.LandingPage`의 `layout`에 위젯 위치와 크기를 저장하는 방식이다. 관리자 편집 화면은 `react-grid-layout`으로 드래그·추가·삭제를 받고, 저장할 때 전체 문서를 JSON Patch로 갱신한다.

```text
Persona 선택
  → GET /api/v1/docStore/name/persona.<FQN>
  → Document.data.pages에서 LandingPage 선택
  → Page.layout의 WidgetConfig 목록을 읽음
  → getWidgetFromKey()가 각 위젯 Component를 렌더링
```

### 5.1 위젯 예시

| Widget key | 화면에서 보이는 정보 |
|---|---|
| `KnowledgePanel.ActivityFeed` | Activity Feed와 협업 흐름 |
| `KnowledgePanel.KPI` | 핵심 지표 |
| `KnowledgePanel.Announcements` | 최근 공지 |
| `KnowledgePanel.MyTask` | 내 작업 |
| `KnowledgePanel.RecentlyViewed` | 최근 조회한 데이터 자산 |
| `KnowledgePanel.Pipeline` | Pipeline 상태 관련 정보 |
| `KnowledgePanel.DataAssets` / `DataProducts` | 데이터 자산·데이터 제품 탐색 |

### 5.2 기본값, 관리자 설정, 개인 선호의 우선순위

Landing Page header 색상처럼 일부 항목은 사용자가 Persona별로 다시 설정할 수 있다. 이때 개인 설정이 있으면 이를 먼저 사용하고, 없으면 관리자가 Persona에 둔 기본값을 사용한다.

```text
사용자 PersonaPreferences
     ↓ 없으면
관리자 UICustomization.personaPreferences
     ↓ 없으면
Theme.panelBackgroundColor 또는 기본 Theme
```

반면 위젯 layout은 Persona의 Page 문서를 기준으로 렌더링된다. 즉 개인 선호와 관리자 레이아웃은 같은 종류의 설정이 아니라, 적용 범위가 다른 두 층이다.

### 5.3 Data Steward 예시

Data Steward용 Persona에서는 Activity Feed, My Task, Announcements, Recently Viewed를 먼저 배치할 수 있다. Data Engineer용 Persona에서는 Pipeline과 Data Quality 관련 위젯의 비중을 높일 수 있다.

중요한 점은 위젯이 “역할 이름”에 직접 하드코딩되지 않는다는 것이다. Persona 문서에 저장된 layout이 어떤 widget key를 어떤 위치에 둘지 결정한다. 그러므로 같은 위젯 구현을 재사용하면서도 역할별 시작 화면을 다르게 만들 수 있다.

## 6. 데모 순서 (10분)

1. `openmetadata-ui/.../package.json`과 `README.md`에서 UI 실행 진입점을 확인한다.
2. `themeConfiguration.json`과 생성된 `uiThemePreference.ts`를 나란히 열어 Schema → Type을 확인한다.
3. Settings → Preferences → Theme에서 Primary Color·Logo·Favicon 설정 항목을 확인한다.
4. `AppRoot.tsx` → `useApplicationStore.ts` → `AntDConfigProvider.tsx` 순으로 테마 전달 경로를 따라간다.
5. Settings → Personas에서 Persona와 사용자 연결을 확인한다.
6. Persona의 Landing Page Customize 화면에서 위젯을 추가·이동·저장한다.
7. `MyDataPage.component.tsx`가 `persona.<FQN>` 문서를 읽고 `getWidgetFromKey()`로 렌더링하는 지점을 확인한다.

## 7. 토론 질문

1. JSON Schema를 바꿨는데 생성 타입을 갱신하지 않으면 UI·Server·Ingestion 중 어디서 어떤 불일치가 먼저 나타날까?
2. Primary Color만 변경했을 때 hover·selected 색을 자동 생성하는 이유는 무엇이며, 언제 명시값으로 고정해야 할까?
3. Persona에 따라 메뉴와 위젯을 줄였을 때 실제 권한 정책은 무엇으로 보장해야 할까?
4. Landing Page widget을 새로 추가하려면 widget Component 외에 어떤 저장 모델·선택 UI·렌더링 매핑을 함께 검토해야 할까?
