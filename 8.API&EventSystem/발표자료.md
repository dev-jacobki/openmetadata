## 1. REST API 설계 규칙

OpenMetadata의 Table, Topic, Dashboard 같은 주요 메타데이터는 엔티티다. 이 엔티티 API들은 비슷한 CRUD 패턴을 많이 공유하지만, 모든 `/api/v1/*` API가 아래 기능을 전부 제공한다는 뜻은 아니다. Table API는 공통 패턴을 설명하기 위한 대표 예시다.

![REST API CRUD 흐름](./발표자료-assets/rest-api-flow.svg)

### 1.1 CRUD 패턴

Table의 기본 경로는 `/api/v1/tables`다.

| 작업 | HTTP 요청 | 의미 |
|---|---|---|
| Create | `POST /v1/tables` | 새로운 Table 생성 |
| Get | `GET /v1/tables/{id}` | ID로 Table 한 건 조회 |
| Get by name | `GET /v1/tables/name/{fqn}` | FQN으로 Table 한 건 조회 |
| List | `GET /v1/tables` | Table 목록 조회 |
| Create or Update | `PUT /v1/tables` | 동일 FQN 엔티티가 없으면 생성, 있으면 갱신 |
| Partial Update | `PATCH /v1/tables/{id}` | 지정한 필드만 변경 |
| Delete | `DELETE /v1/tables/{id}` | Table 삭제 |
| Restore | `PUT /v1/tables/restore` | Soft Delete된 Table 복구 |

#### 1.1.1 POST Create와 PUT Create or Update의 차이

`POST`와 `PUT`은 같은 `CreateTable` 형태의 요청 본문을 사용하지만, 이미 같은 FQN의 Table이 있을 때 동작이 다르다.

| 상황 | `POST /v1/tables` | `PUT /v1/tables` |
|---|---|---|
| 같은 FQN이 없음 | 새 Table 생성, `201 Created` | 새 Table 생성, `201 Created` |
| 같은 FQN이 있음 | `409 Conflict`로 실패 | 기존 Table 갱신, `200 OK` |
| 같은 FQN이 Soft Delete 상태 | `409 Conflict`. 기존 엔티티를 복구하지 않음 | 기존 엔티티를 복구하면서 갱신 |
| 호출 의도 | 반드시 새로 생성 | 있으면 맞추고, 없으면 생성 |

여기서 `PUT`은 OpenMetadata가 이 엔드포인트에 정의한 Upsert 동작이다. 모든 REST API의 `PUT`이 자동으로 Create or Update를 뜻하는 것은 아니다.

```bash
# Create only: 이미 있으면 실패한다.
curl -i -X POST \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  -H "Content-Type: application/json" \
  --data @create-table.json \
  "${OM_API}/v1/tables"

# Create or Update: 같은 FQN이 있으면 갱신한다.
curl -i -X PUT \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  -H "Content-Type: application/json" \
  --data @create-table.json \
  "${OM_API}/v1/tables"
```

그렇다면 항상 `PUT`만 사용해도 되는가? 기술적으로 동기화 작업에는 편하지만, 작업 의도를 구분해야 할 때는 그렇지 않다.

- Ingestion처럼 원본 상태에 맞춰 반복 동기화할 때는 `PUT`이 적합하다. 같은 요청을 다시 보내도 생성 또는 갱신으로 수렴하기 때문이다.
- 사용자가 “새 Table 생성”만 요청한 경우에는 `POST`가 안전하다. 기존 Table을 실수로 갱신하지 않고 충돌로 알려준다.
- “기존 Table 수정”만 허용된 경우에는 대상을 먼저 조회하고 `PATCH`로 필요한 필드만 바꾸는 편이 명확하다.
- Change Request에서 Create와 Update를 별도로 승인한다면 `PUT`의 실제 결과가 어느 쪽인지 반드시 확인해야 한다.

`PUT` 응답은 새로 만들면 `201`, 기존 항목을 처리하면 `200`이다. `X-OpenMetadata-Change` 응답 헤더에서는 `entityCreated`, `entityUpdated`, `entityNoChange`를 구분할 수 있다.

권한 검사도 실행 시점의 결과를 따른다. 대상이 없으면 Create 권한을, 대상이 있으면 Update에 필요한 권한을 검사하므로 `PUT` 호출 권한 하나만 따로 존재한다고 보면 안 된다.

#### 1.1.2 Soft, Hard, Recursive Delete의 관계

삭제는 두 개의 독립된 옵션으로 이해해야 한다.

| 옵션 | `false` | `true` |
|---|---|---|
| `hardDelete` | Soft Delete: `deleted=true`로 표시하고 복구 가능 | Hard Delete: 저장 정보와 관계를 영구 삭제 |
| `recursive` | 대상만 삭제. 삭제되지 않은 하위 엔티티가 있으면 실패 | 포함 관계의 하위 엔티티도 함께 삭제 |

따라서 Recursive Delete는 세 번째 삭제 방식이 아니라 삭제 범위다. 두 옵션을 조합하면 다음 네 가지가 된다.

| `hardDelete` | `recursive` | 결과 |
|---:|---:|---|
| `false` | `false` | 대상만 Soft Delete |
| `false` | `true` | 대상과 하위 엔티티를 모두 Soft Delete |
| `true` | `false` | 대상만 Hard Delete. 하위 엔티티가 있으면 실패 |
| `true` | `true` | 대상과 하위 엔티티를 모두 Hard Delete |

기본값은 두 옵션 모두 `false`다.

##### Table을 Soft Delete하고 확인하기

```bash
curl -i -X DELETE \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  "${OM_API}/v1/tables/${TABLE_ID}"

# 일반 조회에서는 제외되므로 deleted 항목을 포함해 조회한다.
curl -sS \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  "${OM_API}/v1/tables/${TABLE_ID}?include=deleted"
```

Soft Delete 응답의 엔티티에는 `deleted: true`가 표시된다. 일반 목록 조회에서는 보이지 않지만 `include=deleted` 또는 `include=all`로 조회할 수 있다.

##### Soft Delete된 Table 복구하기

```bash
curl -i -X PUT \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  -H "Content-Type: application/json" \
  --data "{\"id\":\"${TABLE_ID}\"}" \
  "${OM_API}/v1/tables/restore"
```

##### Table을 Hard Delete하기

```bash
curl -i -X DELETE \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  "${OM_API}/v1/tables/${TABLE_ID}?hardDelete=true"
```

Hard Delete는 `/restore`로 되돌릴 수 없다. 같은 FQN을 다시 사용하면 복구가 아니라 새로운 ID를 가진 엔티티 생성이 된다.

##### 계층 전체를 Recursive Delete하기

Database Service처럼 하위에 Database, Schema, Table을 포함하는 엔티티에서 차이가 분명하다.

```bash
# 하위 엔티티까지 Soft Delete
curl -i -X DELETE \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  "${OM_API}/v1/services/databaseServices/${SERVICE_ID}?recursive=true"

# 하위 엔티티까지 Hard Delete
curl -i -X DELETE \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  "${OM_API}/v1/services/databaseServices/${SERVICE_ID}?recursive=true&hardDelete=true"
```

`recursive=false`인데 삭제되지 않은 하위 엔티티가 있으면 서버는 “entity is not empty” 오류로 요청을 거절한다. Recursive Hard Delete는 영향 범위가 크고 복구할 수 없으므로 대상 계층과 예상 삭제 건수를 실행 전에 확인해야 한다.

모든 엔티티가 Soft Delete, Restore, Recursive 옵션을 지원하는 것은 아니다. 실제 엔드포인트가 해당 query parameter와 `/restore`를 제공하는지 확인해야 한다.

### 1.2 JSON Patch

`PATCH`는 엔티티 전체를 다시 보내지 않고 바꿀 필드만 전달한다. 요청 본문은 JSON Patch 연산 배열이다.

이 형식은 Table처럼 `PATCH` 엔드포인트가 `application/json-patch+json`을 명시한 경우에만 적용된다. OpenMetadata의 모든 API 요청 본문이 JSON Patch인 것은 아니다.

```http
PATCH /api/v1/tables/{table-id}
Content-Type: application/json-patch+json
If-Match: <현재 ETag>
```

```json
[
  {
    "op": "replace",
    "path": "/description",
    "value": "주문 데이터를 저장하는 테이블"
  }
]
```

주요 연산은 다음과 같다.

| 연산 | 사용 예 |
|---|---|
| `add` | Tag나 Owner 추가 |
| `replace` | Description 변경 |
| `remove` | 기존 Tag 제거 |

조회 응답의 `ETag`를 `If-Match`에 넣으면, 조회 이후 다른 사용자가 먼저 수정한 경우 오래된 데이터로 덮어쓰는 것을 막을 수 있다. 이때 서버는 `412 Precondition Failed`를 반환한다.

### 1.3 `fields` 파라미터

목록과 상세 조회는 기본 필드만 반환한다. Owner, Tag, Column처럼 추가 정보가 필요할 때 `fields`를 지정한다.

```http
GET /api/v1/tables/{table-id}?fields=owners,tags,columns
```

필요하지 않은 필드를 모두 요청하면 응답 크기와 서버 처리량이 커진다. 자동화에서는 실제로 사용하는 필드만 명시하는 편이 좋다.

### 1.4 Pagination

목록 API는 한 번에 전체 결과를 주지 않는다. `limit`와 커서인 `after` 또는 `before`를 사용한다.

```http
GET /api/v1/tables?limit=100
GET /api/v1/tables?limit=100&after=<다음 커서>
```

응답의 `paging.after`가 있으면 다음 페이지가 있다는 뜻이다. 커서가 없어질 때까지 반복하면 전체 목록을 순회할 수 있다.

### 1.5 Versioning

엔티티가 변경되면 버전과 변경 이력이 남는다.

```http
GET /api/v1/tables/{table-id}/versions
GET /api/v1/tables/{table-id}/versions/{version}
```

버전 조회를 이용하면 현재 값만 보는 것이 아니라 어떤 필드가 언제 바뀌었는지 확인할 수 있다.

### 1.6 어디까지 공통 규칙인가

CRUD 표는 OpenMetadata의 주요 버전 관리 엔티티에서 반복되는 공통 패턴이다. 그러나 각 API가 같은 메서드, query parameter, 요청 본문을 모두 지원한다고 가정하면 안 된다.

| 기능 | 주로 적용되는 범위 | 모든 API에 공통인가 |
|---|---|---|
| `POST`, `PUT`, `GET`, `PATCH`, `DELETE` | Table, Topic, Dashboard 같은 엔티티 리소스 | 아니오. 리소스별로 빠진 작업이 있을 수 있음 |
| JSON Patch | `PATCH`와 `application/json-patch+json`을 명시한 엔드포인트 | 아니오 |
| `fields` | 추가 관계 필드를 선택할 수 있는 Get·List | 아니오 |
| `before`, `after`, `limit` | cursor pagination을 제공하는 List | 아니오 |
| `/versions` | 버전을 저장하는 엔티티 | 아니오 |
| `hardDelete`, `recursive`, `/restore` | 해당 삭제 기능을 노출한 엔티티 | 아니오 |

같은 `PUT`이라도 경로에 따라 의미와 본문이 다르다.

| API | 의미 | 요청 본문 |
|---|---|---|
| `PUT /v1/tables` | Table Create or Update | `CreateTable` JSON |
| `PUT /v1/tables/{id}/sampleData` | Sample Data 저장 | `TableData` JSON |
| `PUT /v1/tables/name/{fqn}/import` | CSV로 Table Column 갱신 | CSV 문자열 |
| `PUT /v1/tables/{id}/followers` | Follower 추가 | User ID |

따라서 HTTP 메서드만 보고 동작을 판단하지 않고, **메서드 + 전체 경로 + 요청 Content-Type + 해당 엔드포인트의 스키마**를 함께 확인해야 한다.

## 2. 인증 & SDK

### 2.1 JWT 발급과 Bot 계정

API 호출자는 `Authorization` 헤더에 JWT를 전달한다.

```http
Authorization: Bearer <JWT>
```

사람이 직접 사용하는 계정과 자동화 계정을 분리하기 위해 Bot 계정을 사용한다. Bot에는 필요한 작업만 수행할 수 있는 Role과 Policy를 부여한다.

발급 흐름은 단순하다.

1. 자동화 용도에 맞는 Bot을 만든다.
2. Bot 사용자에게 필요한 Role과 Policy를 연결한다.
3. 해당 Bot용 JWT를 발급한다.
4. 발급한 JWT를 Ingestion 또는 Java 애플리케이션의 Secret으로 저장한다.

예를 들어 조회만 하는 Bot에는 조회 권한만, Tag와 Description을 바꾸는 Bot에는 해당 엔티티의 수정 권한만 부여한다. Ingestion과 Java 애플리케이션도 서로 다른 Bot을 사용하면 실행 주체를 구분하기 쉽다.

### 2.2 LDAP이 담당하는 것

LDAP은 사람 사용자의 아이디와 비밀번호를 중앙 Directory에서 확인하는 인증 방식이다. LDAP 비밀번호를 OpenMetadata의 각 REST API에 직접 보내는 방식은 아니다.

```text
사용자가 이메일·비밀번호 입력
  → OpenMetadata가 LDAP에서 사용자 DN 검색
  → 해당 DN과 비밀번호로 LDAP Bind
  → OpenMetadata 사용자와 Role 확인
  → OpenMetadata가 JWT 발급
  → 이후 UI와 REST API는 JWT 사용
```

역할을 구분하면 다음과 같다.

| 대상 | 인증 방식 |
|---|---|
| 사람이 UI에 로그인 | LDAP 이메일·비밀번호 |
| 로그인한 사람의 API 호출 | 로그인 후 발급된 JWT 또는 개인 Access Token |
| Ingestion, Java 애플리케이션 | 전용 Bot JWT |
| ITSVC 연계 서비스 | 전용 Integration Bot JWT |

즉 LDAP은 사람의 신원을 확인하고, 실제 API 요청 인증은 OpenMetadata가 발급하거나 관리하는 JWT가 담당한다.

### 2.3 LDAP 설정 예시

아래는 구조를 보여 주기 위한 예시다. DN, Attribute 이름, 인증서 위치는 실제 사내 LDAP 스키마에 맞춰야 한다.

```yaml
authenticationConfiguration:
  provider: ldap
  publicKeyUrls:
    - https://metadata.company.com/api/v1/system/config/jwks
  authority: https://metadata.company.com
  enableSelfSignup: false

  ldapConfiguration:
    host: ldap.company.com
    port: 636
    sslEnabled: true

    # 사용자 검색 전용 계정
    dnAdminPrincipal: "cn=om-ldap-reader,ou=service,dc=company,dc=com"
    dnAdminPassword: ${LDAP_READER_PASSWORD}
    userBaseDN: "ou=people,dc=company,dc=com"
    mailAttributeName: mail
    maxPoolSize: 3

    # LDAP Group을 OpenMetadata Role과 연결할 때 사용
    groupBaseDN: "ou=groups,dc=company,dc=com"
    groupAttributeName: objectClass
    groupAttributeValue: groupOfNames
    groupMemberAttributeName: member
    allAttributeName: "*"
    roleAdminName: Admin
    authRolesMapping: >-
      {"cn=om-data-stewards,ou=groups,dc=company,dc=com":["DataSteward"]}
    authReassignRoles: ["DataSteward"]

    truststoreConfigType: CustomTrustStore
    trustStoreConfig:
      customTrustManagerConfig:
        trustStoreFilePath: /opt/openmetadata/conf/company-ldap.p12
        trustStoreFilePassword: ${LDAP_TRUSTSTORE_PASSWORD}
        trustStoreFileFormat: PKCS12
        verifyHostname: true
        examineValidityDates: true
```

주요 설정의 의미는 다음과 같다.

| 설정 | 의미 |
|---|---|
| `dnAdminPrincipal` | 사용자와 Group을 검색하는 Lookup 계정. 전체 관리자일 필요 없음 |
| `userBaseDN` | OpenMetadata 사용자를 찾을 LDAP 검색 범위 |
| `mailAttributeName` | 로그인 입력값과 비교할 이메일 Attribute |
| `groupBaseDN` | Role 매핑에 사용할 Group 검색 범위 |
| `authRolesMapping` | LDAP Group DN을 기존 OpenMetadata Role 이름에 연결 |
| `authReassignRoles` | 로그인할 때 LDAP 기준으로 다시 계산할 Role |
| `sslEnabled` | LDAPS 연결 사용 여부 |
| `truststoreConfigType` | LDAP 서버 인증서를 신뢰하는 방법 |

### 2.4 LDAP 로그인과 OpenMetadata 사용자 생성

LDAP 로그인 과정은 다음 순서로 진행된다.

1. 사용자가 이메일과 비밀번호를 입력한다.
2. OpenMetadata가 `userBaseDN` 아래에서 `mailAttributeName=입력 이메일` 조건으로 검색한다.
3. 검색 결과가 정확히 한 건이면 해당 사용자 DN으로 LDAP Bind를 수행한다.
4. 비밀번호가 맞으면 같은 이메일의 OpenMetadata User를 찾는다.
5. Group 매핑을 사용한다면 LDAP Group을 조회해 OpenMetadata Role을 갱신한다.
6. OpenMetadata JWT를 발급한다.

LDAP 연결은 전체 사용자 목록을 자동으로 가져오는 동기화 기능이 아니다. `enableSelfSignup: false`를 사용할 경우, LDAP에만 있고 OpenMetadata에는 없는 사용자를 사전에 생성해야 한다.

```bash
curl -i -X POST \
  -H "Authorization: Bearer ${ADMIN_OR_PROVISIONING_BOT_TOKEN}" \
  -H "Content-Type: application/json" \
  --data '{
    "name": "gildong.hong",
    "displayName": "홍길동",
    "email": "gildong.hong@company.com",
    "isBot": false
  }' \
  "${OM_API}/v1/users"
```

이때 OpenMetadata에 LDAP 비밀번호를 저장하지 않는다. User 엔티티만 미리 만들고 비밀번호 검증은 로그인 시 LDAP가 담당한다.

OpenMetadata 1.13의 로그인 처리에는 `enableSelfSignup: true`일 때 최초 로그인 사용자를 생성하는 경로가 있지만, LDAP 배포 설정은 `false`를 기본 운영 형태로 안내한다. 사내 환경에서는 사전 프로비저닝과 최초 로그인 생성 중 하나를 정책으로 정하고 혼용하지 않는 편이 안전하다.

### 2.5 ITSVC 사용자와 OpenMetadata 사용자를 연결하는 방법

ITSVC가 같은 사내 LDAP을 사용한다면 ITSVC에서 사용자를 “가져오는” 것이 아니라, 두 시스템이 같은 Directory 사용자를 참조하도록 연결한다.

| ITSVC의 사용자 저장 방식 | 연결 방법 |
|---|---|
| ITSVC와 OpenMetadata가 같은 LDAP 사용 | 공통 LDAP 식별자를 기준으로 같은 사람인지 매핑 |
| 사용자가 ITSVC DB에만 존재 | LDAP으로 조회할 수 없음. ITSVC API·Export 또는 LDAP 프로비저닝 필요 |
| ITSVC와 OpenMetadata가 서로 다른 Directory 사용 | 별도 Directory 동기화 또는 외부 ID 매핑 계층 필요 |

같은 LDAP을 사용하는 경우의 기본 흐름은 다음과 같다.

```text
ITSVC Change Request의 요청자·승인자 ID
  → LDAP에서 고정 식별자로 사용자 한 건 조회
  → email, displayName, group 확인
  → email로 OpenMetadata User 조회
  → 없으면 User API로 사전 생성
  → ITSVC ID ↔ LDAP ID ↔ OpenMetadata User ID 매핑 저장
```

외부 연계 서비스에서는 이메일보다 변경 가능성이 낮은 LDAP Attribute를 기준키로 사용하는 편이 좋다. 실제 Attribute는 사내 Directory 정책에 따라 `employeeNumber`, `uid` 같은 값을 선택한다.

```bash
ldapsearch -LLL \
  -H ldaps://ldap.company.com:636 \
  -D 'cn=itsvc-ldap-reader,ou=service,dc=company,dc=com' \
  -W \
  -b 'ou=people,dc=company,dc=com' \
  '(&(objectClass=person)(employeeNumber=100123))' \
  dn uid employeeNumber mail displayName
```

OpenMetadata의 기본 LDAP 로그인은 이메일로 사용자를 찾으므로, 연계 서비스는 고정 LDAP ID로 사람을 찾은 뒤 현재 이메일을 얻어 OpenMetadata User와 연결하는 형태가 된다.

ITSVC 연계 서비스가 OpenMetadata를 변경할 때는 요청자나 승인자의 LDAP 비밀번호를 사용하지 않는다. 전용 Bot JWT로 API를 호출하고, 실행 기록에 다음 식별자를 함께 남긴다.

- Change Request ID
- ITSVC 요청자·승인자 ID
- LDAP의 고정 사용자 ID
- OpenMetadata User ID
- 실제 API를 호출한 Bot ID

이렇게 해야 “누가 요청하고 승인했는가”와 “어떤 시스템 계정이 API를 실행했는가”를 분리해 추적할 수 있다.

### 2.6 LDAP 적용 시 주의할 점

| 확인 항목 | 주의할 점 |
|---|---|
| 통신 암호화 | 운영에서는 LDAPS를 사용하고 인증서와 Hostname을 검증 |
| Trust Store | `TrustAll`은 테스트 용도로만 사용하고 운영에서는 JVM 또는 사내 Trust Store 사용 |
| Lookup 계정 | 전체 관리자 대신 필요한 Base DN을 읽을 수 있는 전용 Read-only 계정 사용 |
| Secret | Lookup 비밀번호와 Trust Store 비밀번호를 Git이나 설정 파일에 평문 저장하지 않음 |
| 검색 범위 | `userBaseDN`, `groupBaseDN`을 필요한 조직 범위로 제한 |
| 사용자 유일성 | 로그인 이메일 검색 결과가 0건 또는 2건 이상이면 인증 실패. LDAP의 `mail` 중복 방지 필요 |
| 식별자 | 이메일과 이름은 바뀔 수 있으므로 ITSVC 매핑 키로만 사용하지 않음 |
| 사용자 이름 | 이메일 앞부분으로 이름을 만들면 서로 다른 도메인의 같은 계정명이 충돌할 수 있음 |
| Role 매핑 | LDAP Group DN과 OpenMetadata Role 이름을 정확히 맞추고 Group 변경 후 재로그인 동작 확인 |
| 사용자 퇴사·잠금 | LDAP 로그인 차단뿐 아니라 기존 JWT·개인 Token의 만료와 회수 정책도 함께 확인 |
| 대량 동기화 | LDAP 전체 검색을 반복하지 말고 제한된 Base DN, Filter, paging과 증분 기준 사용 |

### 2.7 curl, Python SDK, Java SDK의 관계

세 방식 모두 결국 같은 REST API를 호출한다.

| 방식 | 적합한 사용 | 특징 |
|---|---|---|
| curl | API 확인, 장애 분석, 간단한 스크립트 | HTTP 요청과 응답을 그대로 확인 가능 |
| Python SDK | Ingestion, 배치, 데이터 작업 | 엔티티 모델과 `ometa` 편의 메서드 제공 |
| Java SDK | Java 서비스 내부 연동 | Java 모델과 API 클라이언트 사용 |

SDK를 사용해도 HTTP의 의미는 바뀌지 않는다.

| 작업 | REST API | Python SDK에서의 형태 | Java에서의 형태 |
|---|---|---|---|
| Create | `POST` | `create(...)` | Create 요청 모델을 API 클라이언트로 전송 |
| Create or Update | `PUT` | `create_or_update(...)` | Create or Update API 호출 |
| Partial Update | `PATCH` | `patch(...)`, `patch_tags(...)`, `patch_description(...)` | JSON Patch와 필요 시 ETag 전달 |
| Delete | `DELETE` | `delete(...)` | Delete API 호출 |

서버와 SDK의 모델이 달라지면 필드 직렬화나 API 호환 문제가 생길 수 있으므로 버전을 함께 맞춰야 한다.

## 3. Event System

Event System은 OpenMetadata에서 성공한 변경을 외부 시스템에 전달한다.

![Event System 흐름](./발표자료-assets/event-system-flow.svg)

### 3.1 ChangeEvent 구조

ChangeEvent에는 어떤 엔티티에 어떤 변경이 발생했는지가 들어간다.

```json
{
  "id": "event-uuid",
  "eventType": "entityUpdated",
  "entityType": "table",
  "entityId": "table-uuid",
  "entityFullyQualifiedName": "service.database.schema.orders",
  "timestamp": 1785110400000,
  "userName": "ingestion-bot",
  "changeDescription": {
    "fieldsUpdated": [
      {
        "name": "description",
        "oldValue": "",
        "newValue": "주문 데이터 테이블"
      }
    ]
  }
}
```

확인할 핵심 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `id` | 이벤트 식별자. 중복 처리 방지에 사용 가능 |
| `eventType` | 생성·수정·삭제 등 발생한 이벤트 종류 |
| `entityType` | Table, Topic 등 엔티티 종류 |
| `entityId` | 변경된 엔티티 ID |
| `entityFullyQualifiedName` | 변경된 엔티티 FQN |
| `timestamp` | 이벤트 발생 시각 |
| `userName` | 변경을 실행한 사용자 또는 Bot |
| `changeDescription` | 추가·수정·삭제된 필드 정보 |

### 3.2 EventType

엔티티 C/U/D에서 주로 보는 이벤트는 다음과 같다.

| EventType | 의미 |
|---|---|
| `entityCreated` | 엔티티 생성 |
| `entityUpdated` | 엔티티의 주요 내용 변경 |
| `entityFieldsChanged` | 특정 필드 변경 |
| `entitySoftDeleted` | Soft Delete |
| `entityDeleted` | 영구 삭제 |
| `entityRestored` | Soft Delete 상태에서 복구 |

Thread, Post, Task에도 별도 생성·수정·종료 이벤트가 있다.

### 3.3 EventFilter

모든 변경을 같은 곳으로 보내면 불필요한 알림이 많아진다. EventFilter는 필요한 이벤트만 선택한다.

선별 기준으로는 다음 항목을 사용할 수 있다.

- Table 같은 엔티티 유형
- Create, Update, Delete 같은 이벤트 유형
- 특정 엔티티 ID 또는 FQN
- 변경을 실행한 사용자나 Bot
- 변경된 필드
- Domain과 Owner

예를 들어 Table의 Column 변경만 받으려면 엔티티 유형을 Table로 제한하고, 변경 필드 조건에 Column 관련 필드를 지정한다.

Tier Tag 자체를 필터 조건으로 직접 사용하기 어렵다면 Webhook 수신기가 이벤트의 엔티티를 조회한 뒤 Tier를 확인해야 한다.

### 3.4 Webhook과 Slack 연동

Webhook은 조건에 맞는 이벤트를 외부 HTTP 주소로 전송한다. 수신기는 정상 처리 시 `2xx`를 반환해야 한다.

Slack으로 바로 알릴 수도 있지만, 조건 판단과 중복 제거가 필요하면 중간에 내부 Webhook 수신기를 두는 편이 명확하다.

```text
OpenMetadata
  → Webhook 수신기
  → 이벤트 중복 확인
  → Table 정보와 Tier 확인
  → Slack 메시지 전송
```

이벤트 수신기는 다음 상황을 처리해야 한다.

- 같은 이벤트가 다시 와도 한 번만 처리
- 이벤트 순서가 바뀌어도 현재 엔티티 상태를 기준으로 판단
- Slack 전송 실패 시 재시도하거나 실패 기록 보관
- 처리하지 못한 이벤트를 다시 실행할 수 있도록 원문 보관

ChangeEvent는 API 변경이 성공한 뒤 발생한다. 따라서 변경 전에 승인을 확인하거나 API 실행 자체를 차단하는 용도로 사용할 수 없다.

## 4. Activity Feed & Thread

Activity Feed는 데이터 자산을 중심으로 대화, 작업, 공지를 남기는 기능이다.

![Activity Feed와 Thread 구조](./발표자료-assets/activity-feed-flow.svg)

### 4.1 Thread와 Post

Thread는 대화의 시작점이고 Post는 해당 Thread에 달리는 답글이다.

```text
Table 또는 특정 Column
└─ Thread
   ├─ 최초 메시지
   ├─ Post 1
   └─ Post 2
```

Thread는 Table 전체뿐 아니라 Description이나 Column 같은 특정 필드에도 연결할 수 있다. 이 때문에 어떤 데이터의 어느 부분에 대한 대화인지 함께 남길 수 있다.

### 4.2 Conversation

일반적인 질문과 답변에 사용한다. 데이터 의미 확인, 담당자 문의, 변경 내용 공유 같은 대화를 한곳에 모을 수 있다.

### 4.3 Task

Description 추가나 Tag 확인처럼 담당자에게 실제 작업을 요청할 때 사용한다. 담당자, 상태, 작업 내용을 함께 관리할 수 있다.

### 4.4 Announcement

일정 기간 노출해야 하는 공지에 사용한다. 스키마 변경 예정, 데이터 사용 중단, 장애 안내처럼 시작 시각과 종료 시각이 있는 메시지에 적합하다.

### 4.5 @mention

메시지에서 사용자나 팀을 언급해 해당 대화로 호출한다. 단순 댓글과 달리 누가 확인해야 하는지 명확하게 전달할 수 있다.

Activity Feed는 협업 기록이고 ChangeEvent는 시스템 변경 기록이다. 둘은 목적이 다르다.

| 구분 | Activity Feed & Thread | ChangeEvent |
|---|---|---|
| 중심 | 사람의 대화와 작업 | 엔티티 변경 사실 |
| 생성 방식 | 사용자가 대화·Task·공지를 작성 | API 변경 성공 후 시스템이 생성 |
| 주요 사용 | 문의, 협업, 담당자 호출 | 자동화, 감사, 외부 알림 |

## 5. API와 SDK 사용 예시

### 5.1 Bot JWT로 Table 목록 조회

```bash
export OM_API='http://localhost:8585/api'
export OM_TOKEN='<BOT_JWT>'

curl -sS \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  "${OM_API}/v1/tables?limit=10&fields=owners,tags"
```

응답에서 확인할 값은 `data`, `paging.after`, 각 Table의 `id`, `fullyQualifiedName`이다.

### 5.2 특정 Table 상세 조회

```bash
export TABLE_ID='<TABLE_UUID>'

curl -sS \
  -H "Authorization: Bearer ${OM_TOKEN}" \
  "${OM_API}/v1/tables/${TABLE_ID}?fields=owners,tags,columns"
```

목록 조회에서 얻은 Table ID를 사용하면 FQN의 특수 문자를 별도로 URL 인코딩할 필요가 없다.

### 5.3 Python SDK로 Tag 추가와 Description 변경

아래 예시는 `metadata`가 Bot 인증 정보로 초기화된 `OpenMetadata` 클라이언트라고 가정한다.

```python
from metadata.generated.schema.entity.data.table import Table
from metadata.generated.schema.type.tagLabel import (
    LabelType,
    State,
    TagFQN,
    TagLabel,
    TagSource,
)

table = metadata.get_by_name(
    entity=Table,
    fqn="service.database.schema.orders",
    fields=["tags"],
)

metadata.patch_tags(
    entity=Table,
    source=table,
    tag_labels=[
        TagLabel(
            tagFQN=TagFQN("Tier.Tier1"),
            labelType=LabelType.Automated,
            state=State.Suggested,
            source=TagSource.Classification,
        )
    ],
    skip_on_failure=False,
)

metadata.patch_description(
    entity=Table,
    source=table,
    description="주문 데이터를 저장하는 테이블",
    force=True,
    skip_on_failure=False,
)
```

`skip_on_failure=False`로 두면 수정 실패가 조용히 넘어가지 않고 예외로 드러난다. 승인 후 실행 결과를 정확히 남겨야 하는 작업에서는 실패를 명확히 감지해야 한다.

### 5.4 Webhook으로 변경 이벤트 확인

1. Table의 Update 이벤트를 받는 Event Subscription을 만든다.
2. 수신할 HTTPS 주소를 Generic Webhook 대상으로 등록한다.
3. Table Description이나 Tag를 변경한다.
4. 수신한 JSON에서 `eventType`, `entityId`, `userName`, `changeDescription`을 확인한다.
5. 정상 처리 후 `2xx`를 반환한다.

수신 로그에는 최소한 이벤트 ID, 엔티티 ID, 이벤트 유형, 처리 결과를 남겨야 중복과 실패를 추적할 수 있다.

## 6. Change Request 연계 시 중요하게 볼 부분

승인 상태와 업무 절차는 ITSVC의 결과를 그대로 사용한다. 여기서는 Ingestion과 Java의 C/U/D를 실제 API 실행 및 이벤트와 연결할 때 필요한 기술 항목만 다룬다.

![ITSVC Change Request와 OpenMetadata 변경 흐름](./발표자료-assets/change-request-flow.svg)

### 6.1 승인은 API 호출 전에 확인해야 한다

ChangeEvent는 변경 후에 발생하므로 승인 여부를 확인하는 위치가 될 수 없다. Ingestion과 Java가 OpenMetadata 변경 API를 호출하기 직전에 ITSVC 상태를 확인해야 한다.

```text
승인 요청
  → 승인: 실행 직전 상태 재확인 → OpenMetadata C/U/D 실행
  → 반려: OpenMetadata 호출 안 함
  → 취소: OpenMetadata 호출 안 함
```

승인 확인과 API 호출 사이에 취소될 수 있으므로, 오래 전에 확인한 승인 결과를 계속 사용하지 않고 실행 직전에 다시 확인해야 한다.

### 6.2 공통 실행 지점이 필요하다

Ingestion과 Java가 각자 다른 방식으로 승인 상태를 확인하면 누락되는 경로가 생긴다. OpenMetadata에 C/U/D를 보내기 전 반드시 통과하는 공통 실행 지점을 두고 같은 규칙을 적용해야 한다.

공통 지점에서 확인할 값은 다음과 같다.

| 확인 항목 | 필요한 이유 |
|---|---|
| Change Request ID | 승인 요청과 실제 실행 결과 연결 |
| 현재 상태 | 승인 상태일 때만 실행 |
| 요청한 작업 C/U/D | 승인받은 작업과 실제 HTTP 작업 비교 |
| 엔티티 유형과 ID·FQN | 승인받은 대상과 실제 대상 비교 |
| 요청 본문 해시 | 승인 후 payload가 바뀌었는지 확인 |
| 기준 버전 또는 ETag | 승인 후 다른 변경이 있었는지 확인 |
| 요청자·승인자 식별자 | ITSVC ID, LDAP 고정 ID, OpenMetadata User ID 연결 |
| 실행 Bot | 어느 경로가 변경했는지 구분 |

### 6.3 C/U/D를 정확히 구분해야 한다

| 작업 | 주의할 부분 |
|---|---|
| Create | 같은 FQN이 이미 생겼는지 실행 직전 확인 |
| Update | 승인 당시 버전과 현재 버전 비교, PATCH에는 ETag 사용 |
| Delete | `hardDelete`와 `recursive` 조합이 승인 내용과 같은지 확인 |
| PUT | 실행 시점에 Create 또는 Update가 되므로 예상 작업 재확인 |
| Bulk | 일부 성공과 일부 실패가 함께 발생할 수 있으므로 건별 결과 기록 |

특히 `PUT` Create or Update를 단순 Update로 취급하면, 대상이 없을 때 승인받지 않은 Create가 될 수 있다.

### 6.4 Change Request ID와 ChangeEvent를 연결해야 한다

기본 ChangeEvent에는 ITSVC Change Request ID 필드가 없다. API 요청 헤더에 ID를 넣는 것만으로는 ChangeEvent에 자동 저장되지 않는다.

따라서 별도의 실행 기록에서 다음 관계를 남겨야 한다.

```text
Change Request ID
  ↔ 실행 요청 ID
  ↔ 대상 엔티티와 작업
  ↔ API 응답
  ↔ ChangeEvent ID
```

이 연결이 있어야 승인된 요청이 실제로 실행되었는지, 이벤트가 어떤 요청에서 발생했는지 확인할 수 있다.

### 6.5 Ingestion에서 생길 수 있는 문제

Ingestion은 원본과 OpenMetadata를 반복해서 동기화한다. 실제 차이가 없는데도 매번 C/U/D 대상으로 판단하면 승인 요청과 이벤트가 불필요하게 늘어난다.

미리 처리할 부분은 다음과 같다.

- 현재 엔티티와 원하는 상태를 비교해 실제 변경이 있는 항목만 요청
- 한 번의 실행에서 예상되는 Create, Update, Delete 목록을 실행 전에 확정
- 승인 이후 payload와 대상 목록이 바뀌면 기존 승인을 사용하지 않음
- 재실행할 때 이미 성공한 작업을 다시 변경하지 않도록 멱등성 확보
- 삭제 탐지 시 Soft·Hard·Recursive 범위를 명확히 구분

### 6.6 Java에서 생길 수 있는 문제

Java 애플리케이션에서 여러 위치가 직접 SDK나 REST API를 호출하면 승인 확인을 우회할 수 있다.

미리 처리할 부분은 다음과 같다.

- C/U/D 호출을 공통 클라이언트 또는 공통 서비스로 모음
- 공통 지점에서 ITSVC 상태, 대상, 작업, payload를 검증
- 직접 curl, 공용 관리자 Token, 별도 SDK 클라이언트 같은 우회 경로 제한
- `409`, `412`, `429`, `5xx`, timeout을 서로 다른 결과로 기록
- timeout 후 무조건 재호출하지 말고 실제 반영 여부를 먼저 확인

### 6.7 취소와 실패의 의미를 구분해야 한다

| 상황 | 처리 |
|---|---|
| API 호출 전 취소 확인 | 호출하지 않음 |
| API 처리 중 취소 | 성공 여부를 API 응답과 엔티티 상태로 확인 |
| API 성공 후 취소 | 이미 발생한 변경이므로 자동으로 원복되지 않음 |
| API 실패 | 실패 원인과 재시도 여부 기록 |
| API 성공, 이벤트 미수신 | 엔티티 상태와 이벤트 전달 상태를 별도로 확인 |

승인 상태, API 실행 결과, 이벤트 전달 결과는 서로 다른 상태다. 하나의 성공 여부로 합치지 말고 각각 기록해야 한다.

### 6.8 승인한 사람과 실행한 Bot을 구분해야 한다

ITSVC 요청자와 승인자는 LDAP로 식별되는 사람이고, OpenMetadata C/U/D를 호출하는 주체는 Integration Bot이다. API의 `updatedBy`만 보면 Bot만 보일 수 있으므로 별도 실행 기록에 사람과 Bot을 함께 남겨야 한다.

```text
요청자·승인자: ITSVC ID ↔ LDAP 고정 ID ↔ OpenMetadata User ID
실행 주체: Integration Bot ID
실행 대상: Entity ID·FQN + C/U/D + payload hash
실행 결과: HTTP status + ChangeEvent ID
```

LDAP 이메일이나 Display Name이 나중에 바뀌더라도 과거 승인자를 확인할 수 있도록 승인 시점의 표시값과 고정 식별자를 함께 보관한다. LDAP 비밀번호나 개인 Access Token은 실행 기록과 연계 데이터에 저장하지 않는다.

## 7. 자동화에 적용할 내용

### 7.1 기존 자동화 스크립트에서 API 사용

기존 스크립트는 다음 순서로 구성할 수 있다.

```text
Bot 인증
  → 대상 조회
  → 현재 값과 원하는 값 비교
  → 변경이 있을 때만 승인 상태 확인
  → C/U/D 호출
  → API 결과 기록
  → ChangeEvent와 연결
```

조회 작업은 `fields`와 pagination을 사용하고, 수정 작업은 가능한 경우 PATCH와 ETag를 사용한다. 작업 실패를 성공처럼 넘기지 않도록 HTTP 상태 코드와 SDK 예외를 반드시 확인한다.

### 7.2 Tier1 Table의 스키마 변경을 Slack으로 알리기

다음과 같이 구성할 수 있다.

```text
Table Column 변경
  → ChangeEvent 발생
  → Table·Column 변경 이벤트만 필터링
  → 내부 Webhook 수신기
  → 현재 Table의 Tier 확인
  → Tier1이면 Slack 전송
```

Slack 메시지에는 Table FQN, 변경된 Column, 변경 전후 값, 변경 사용자, 발생 시각을 넣는다. 같은 `event.id`가 다시 들어오면 중복 전송하지 않는다.

### 7.3 Rate limit과 대량 호출

환경마다 처리 가능한 호출량이 다르므로 고정된 초당 요청 수를 가정하지 않고 실제 환경에서 측정해야 한다.

대량 처리에서는 다음 항목을 적용한다.

- 목록은 pagination으로 순차 조회
- 필요한 값만 `fields`로 요청
- 무제한 병렬 호출 대신 동시 실행 수 제한
- `429` 응답의 재시도 시점을 따르고 지수 Backoff 적용
- Create·Update 전 현재 상태를 비교해 불필요한 호출 제거
- Bulk 요청은 전체 성공으로 가정하지 않고 항목별 결과 확인
- 재시도해도 중복 변경이 생기지 않도록 멱등성 확보

API 호출 성공과 이벤트 전달 성공은 별개이므로, 대량 작업에서는 API 처리 건수와 이벤트 수신 건수를 각각 확인한다.
